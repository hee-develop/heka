# heka2 설계 초안

> 상태: 초안. 마지막으로 고친 날은 2026-11-13이다. 범위·개입 수준·등록 자격·우선순위는 정해졌다. "제안"이라고 적힌 숫자와 7장의 열린 결정은 확정이 아니다.
> 논의 경과는 저장소에 올리지 않는 로컬 기록에 남긴다. 이 문서의 예시는 전부 지어낸 것이다.

## 1. 정의와 원칙

**heka는 AI 에이전트가 일하는 각 순간에, 그 순간에 필요한 컨텍스트만 골라 행동 전에 전달하고, 그 전달이 맞았는지 기록으로 확인하는 개인용 컨텍스트 주입기다.**

본체는 주입이다. 저장·검수 같은 관리 기능은 주입 품질을 올리는 데 필요한 만큼만 둔다.

원칙은 여섯 가지다.

1. **주입이 본체, 관리는 보조.** 어떤 기능이든 "이것이 주입을 더 정확하게 만드는가"로 넣을지 정한다.
2. **확신이 없으면 침묵한다.** 무관한 주입은 주입이 없는 것보다 나쁘다. 주입 줄 전체를 믿지 않게 만든다.
3. **주입문만 읽고 행동할 수 있어야 한다.** 제목을 주고 본문을 찾아 읽게 하지 않는다.
4. **모든 주입은 설명할 수 있어야 한다.** 무엇을, 어떤 조건이 맞아서 넣었는지 한 줄로 남긴다.
5. **사람이 읽는 파일이 정본이다.** 그 밖의 것은 지우고 다시 만들 수 있다.
6. **작게 만든다.** 한 화면 도식으로 설명할 수 없는 구성 요소는 넣지 않는다.

구성 요소는 다섯 개다.

| 구성 요소 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 항목 파일 | 주입 단위 하나를 마크다운 파일 하나로 보관한다 | 원문 사본 저장 |
| 선별기 | "지금 이 순간"을 받아 넣을 항목과 형태를 정한다 | 클라이언트 형식 해석 |
| 연결부 | 클라이언트의 이벤트를 선별기 입력으로, 선별 결과를 클라이언트 출력으로 바꾼다 | 무엇을 넣을지 판단 |
| 원장 | 주입과 사건(교정, 위반)을 한 줄씩 기록한다 | 판단에 개입 |
| 재현기 | 기록된 순간을 선별기에 다시 넣어 성공 조건을 잰다 | 실사용 경로에 개입 |

## 2. 해야 하는 일

### 2.1 요구사항

| # | 요구 | 풀려는 문제 |
|---|---|---|
| R1 | 정해진 순간마다 주입한다(2.2) | 지적한 것이 반복됨 |
| R2 | 관련 있는 것만 넣고, 확신이 없으면 넣지 않는다 | 지적한 것이 반복됨 |
| R3 | 주입문은 그대로 행동 지침이 된다 | 전달됐는데 지키지 않음 |
| R4 | 주입마다 내용·이유·시각을 기록하고 한 명령으로 조회한다 | 무엇을 하는지 안 보임 |
| R5 | 주입되는 항목마다 출처, 사람 확인 여부, 유효기한을 가진다 | 내용을 믿기 어려움 |
| R6 | 사용자의 교정은 등록된 직후부터 주입 대상이 된다 | 지적한 것이 반복됨 |
| R7 | 선별기는 어떤 AI 도구인지 모른다 | 플랫폼 종속 |
| R8 | 항목은 사람이 편집기로 읽고 고칠 수 있다 | 내용을 믿기 어려움 |
| R9 | heka가 실패해도 작업은 계속된다 | 단일 장애점 |
| R10 | 전체 구조를 사용자가 직접 설명할 수 있는 크기로 유지한다 | 너무 크고 이해가 안 됨 |
| R11 | 기계가 검사할 수 있는 규칙은 결과물을 직접 검사한다 | 전달됐는데 지키지 않음 |
| R12 | 사용자가 그 턴에 시킨 일에는 확인을 다시 묻지 않는다 | 불필요한 확인 |
| R13 | 비슷한 항목이 이미 있으면 등록 전에 결정을 받는다 | 내용을 믿기 어려움 |

### 2.2 주입하는 순간

| 순간 | 선별기가 받는 것 | 넣는 것 |
|---|---|---|
| 세션 시작, 압축 직후 | 작업 위치 | 그 범위의 필수 항목 목록 |
| 사용자 프롬프트 | 프롬프트 글 | 주제어가 일치하는 항목(최대 3건)과, 프롬프트가 시킨 동작에 조건이 걸린 필수 항목 (3.2) |
| 도구 호출 직전 | 동작 이름, 대상 경로, 명령 | 조건이 일치하는 필수 항목 본문 |
| 서브에이전트 시작 | 에이전트 종류, 위임 글 | 범위의 필수 항목과 주제 일치 항목 |
| AI 또는 사람의 조회 | 질의 | 검색된 항목 본문 |
| 턴 종료 | 마지막 응답 | 넣지 않는다. 결과물 검사에 걸렸을 때만 사유를 돌려준다 (3.3) |

도구가 만들어 넣은 프롬프트(하위 에이전트의 완료 알림 등)는 프롬프트 순간으로 보지 않는다(2026-11-13 결정). 그 글로 항목을 찾지 않고, 말로 한 허용도 읽지 않는다. 사용자의 지시가 아니고, 글이 길어 주제어가 우연히 겹치기 쉽기 때문이다. 사용자가 쓴 프롬프트인지는 연결부가 가린다.

### 2.3 하지 않는 일

초안에서는 아래를 만들지 않는다(2026-11-13 결정). 주입에 직접 기여하지 않거나, 기존 heka에서 사용 실적이 거의 없었다. 지식은 대화 중 등록과 사람의 직접 편집으로만 들어온다.

- 외부 문서·메신저·이슈 추적기의 원문 수집과 사본 보관
- LLM이 밤에 도는 자동 추출·판정·정리 작업
- 웹 화면, 그래프, 묶음(컬렉션), 절차 실행기
- 임베딩 검색과 벡터 DB (뜻의 신호가 필요한지는 재현 결과로 정한다. 4.3)

### 2.4 heka에 넣는 것과 넣지 않는 것

기준은 하나다. 지식이 에이전트를 따라다니면 에이전트 정의에 두고, 상황(어느 저장소인지, 어떤 동작인지, 누구의 일인지)을 따라다니면 heka에 둔다.

| 넣는 것 | 예 | 주입 |
|---|---|---|
| 규칙·선호 | 커밋 메시지는 한국어로 쓴다 | 필수, 동작 조건 |
| 용어·사실 | 여기서 "주문"은 결제가 끝난 건만 뜻한다 | 참고, 주제어 |
| 결정과 이유 | 색인은 다시 만들 수 있는 파일로 둔다 | 참고, 프로젝트 범위 |
| 진행 상태 | 결제 화면 개편은 2단계까지 끝났다 | 참고, 기한 필수 |
| 가리키는 말 | PR은 전용 스킬로 만든다 | 필수 또는 참고 |

| 넣지 않는 것 | 대신 두는 곳 |
|---|---|
| 에이전트의 역할과 완료 기준 | 에이전트 정의 |
| 여러 단계의 절차 | 스킬 |
| 기계가 검사할 수 있는 규칙의 집행 | 린트, 테스트, 훅의 결과물 검사 |
| 코드에서 읽을 수 있는 것 | 저장소 |
| 문서 원문 | 원래 있던 곳. heka에는 링크만 |

### 2.5 교훈을 두는 자리

에이전트가 실수했을 때 교훈을 어디에 둘지는 위에서부터 묻는다. 위쪽일수록 지켜질 보장이 강하다.

```
0. 먼저 원장에 사건으로 남긴다 (항상)
1. 기계가 잡아낼 수 있는가            → 검사로 만든다 (린트·테스트·훅의 결과물 검사)
2. 그 에이전트라면 어디서든 해당하는가  → 에이전트 정의를 고친다
3. 특정 저장소·팀·사람의 사정인가      → heka 항목으로 등록한다
4. 여러 단계로 된 방법인가            → 스킬로 만든다. heka에는 그 스킬을 쓰라는 한 줄만
5. 고친 뒤에는 그 상황을 재현 세트에 넣는다
```

- 내장 에이전트나 남이 만든 에이전트처럼 정의를 고칠 수 없으면 2를 건너뛰고 heka가 맡는다.
- heka 항목이 전달됐는데도 거듭 어겨지면 원장에 드러난다. 그 항목은 검사나 에이전트 정의로 올린다.
- 운영 방식(2026-11-13 결정): 교훈은 일단 heka에 받는다. 위 순서에 따라 에이전트 정의·스킬·검사로 옮기는 일은 heka와 무관하게 도는 별도 과정이 주기적으로 한다. heka는 그 과정이 쓸 창구만 낸다(4.9).

## 3. 개념 모델

### 3.1 항목

주입 단위 하나가 파일 하나다.

```markdown
---
id: commit-message-language
text: 커밋 메시지는 한국어로 쓰고 첫 줄은 50자 이내로 한다.
must: true
when:
  action: git.commit
about: [커밋 메시지, commit message]
scope: [repo/sample-app]
source: user
quote: "커밋 메시지는 한국어로 써 줘. 첫 줄은 짧게."
checked: 2026-11-13
expires:
confirm: false
---
배경과 예시. 조회할 때만 읽힌다.
```

| 필드 | 뜻 |
|---|---|
| `text` | 주입문. 한두 문장이고 이것만 읽어도 행동할 수 있어야 한다 |
| `must` | 반드시 지킬 것인가(true), 알면 좋은 것인가(false) |
| `when` | 구조로 판정하는 조건: 순간, 동작, 경로, 저장소, 에이전트 종류 |
| `about` | 주제어. 프롬프트·위임 글과 견준다. 동작 조건이 붙은 항목에서는 조회에만 쓴다 (3.2) |
| `scope` | 주입해도 되는 범위. 범위 밖에서는 후보에도 들지 않는다 |
| `source` | 누가 말했는가: user, doc, ai |
| `quote` | `source: user`일 때 근거가 되는 사용자 발화. 등록할 때 세션 기록과 대조해 실제로 있는 말인지 확인한다 |
| `checked` | 사람이 확인한 날. 비어 있으면 미확인 |
| `expires` | 유효기한. 지나면 주입하지 않고 점검 목록에 올린다 |
| `confirm` | false(기본)는 알리기만 한다. true는 사용자가 그 턴에 시킨 일이 아니면 확인을 요구한다. always는 시킨 일이어도 매번 확인한다 (3.3) |
| `check` | 선택. 결과물 검사 (3.3) |

같은 id의 내용이 바뀌면 파일을 고친다. 이력은 git이 보관한다.

### 3.2 선별 순서

순서는 고정이고 단계마다 탈락 사유가 원장에 남는다.

```
범위 → 자격 → 일치 → 중복 제거 → 예산 → 형태
```

- **범위**: 작업 위치로 정한 범위에 속한 항목만 후보가 된다. 범위를 알 수 없으면 전역 항목만 본다.
- **자격**: 기한이 지난 항목은 탈락한다. 사람이 확인한 항목은 통과한다. 미확인 항목은 출처에 따라 다르다.

  | 출처 | 미확인일 때 |
  |---|---|
  | user, 대조된 `quote` 있음 | 통과. 등록 직후부터 주입된다 |
  | user, `quote` 없음 | 탈락 |
  | doc | 참고로만 통과. 필수 항목이 될 수 없다 |
  | ai | 탈락 |
- **일치**: `when`은 구조 비교로, `about`은 주제어 일치로 판정한다. 본문 어휘만 겹치는 경우는 희소한 단어에 가중을 주고 글 길이로 정규화한 값이 문턱을 넘을 때만 인정한다. 문턱은 재현 결과로 정한다.

  동작 조건이 붙은 항목(행동 규칙)은 프롬프트의 낱말이나 주제어로 찾지 않는다(2026-11-13 결정). 프롬프트가 그 동작을 시키면 동작 낱말 사전(3.3)으로 알아채 미리 주고, 그렇지 않으면 도구 호출 직전에 준다. 이런 항목의 `about`은 조회와, 등록할 때 비슷한 항목을 찾는 데만 쓴다.
- **중복 제거**: 같은 항목은 세션에 한 번만 넣는다. 압축 직후에는 다시 넣는다.
- **예산**: 순간마다 토큰 상한이 있다. 넘치면 필수 항목을 먼저 남긴다.
- **형태**: 필수 항목은 `text` 전문, 참고 항목은 `text`와 id.

관련도와 신뢰를 한 점수로 합치지 않는다. 신뢰는 자격 단계에서 걸러내는 데만 쓴다.

### 3.3 행동 시점의 개입

도구 호출 직전에 조건에 걸린 항목은 세 갈래로 처리된다. 세 갈래 모두 원장에 한 줄을 남긴다.

| 항목 | 처리 |
|---|---|
| 알리기만 하는 항목 (`confirm: false`) | 주입문을 넣고 진행한다 |
| 확인을 요구하는 항목 (`confirm: true`) | 사용자가 그 턴에 시킨 일이면 진행하고, 아니면 사용자에게 확인을 요구한다 |
| 검사가 붙은 항목 (`check`) | 결과물이 형식에 맞으면 진행하고, 아니면 막고 사유를 모델에게 돌려준다 |

**동작 낱말 사전.** 프롬프트가 어떤 동작을 시키는지는 동작별 표현을 적은 사전 하나로 알아챈다("푸시해 줘" → `git.push`). 사전은 두 곳에 쓰인다(2026-11-13 결정).

- 미리 주기: 프롬프트가 시킨 동작에 조건이 걸린 필수 항목을 프롬프트 순간에 준다. 사전이 알아채지 못하면 도구 호출 직전에 준다.
- 말로 한 허용: 그 동작의 허용을 세션 상태에 적는다.

부정("하지 마"), 질문("해도 돼?"), 조건("하기 전에")이 섞이면 시킨 것으로 보지 않는다. 사전은 설정 파일에 둔다. 저장소에는 한국어와 영어의 최소 목록(푸시, 커밋, PR)만 예시 설정 파일로 싣는다(2026-11-13 결정).

**말로 한 허용.**

- 허용은 그 턴이 끝나면 사라진다. "이번 세션 동안 계속"이라고 하면 세션 동안 남는다.
- 금지 표현은 이미 준 세션 허용도 거둔다.
- 도구가 만들어 넣은 프롬프트로 이어지는 처리는 같은 턴으로 본다. 그런 프롬프트는 허용을 만들지도 끝내지도 않는다(2.2).

**결과물 검사.**

```yaml
check:
  target: commit_message     # command · commit_message · pr_body · last_message
  pattern: "^.{1,50}(\n|$)"  # 맞아야 하는 형식. not_pattern 은 있으면 안 되는 표현
  mode: block                # block 은 막고, log 는 기록만 한다
```

- 명령, 커밋 메시지, PR 본문은 도구 호출 직전에 명령에서 뽑아 검사한다. 파일로 넘겨서 뽑을 수 없는 경우는 검사하지 않는다.
- 마지막 응답은 턴이 끝날 때 검사한다. 걸리면 모델을 한 번 더 돌게 하되 세션당 3회까지만 한다.
- 정규식은 Go 표준 문법이다. 앞뒤 살피기 문법은 없지만 시간 상한이 필요 없다.
- 식이 틀렸거나 heka가 실패하면 통과시킨다(R9).

### 3.4 등록

1. 검증한다: 필수 필드, 주제어 1개 이상, 필수 항목이면 조건, 진행 상태면 기한.
2. 비슷한 항목을 찾는다: 같은 조건(동작과 범위), 겹치는 주제어, 글의 겹침.
3. 없으면 바로 쓰고 색인을 교체한다.
4. 있으면 대기함(`items/_pending/`)에 두고 후보를 돌려준다. 대기함의 항목은 주입하지 않는다.

| 결정 | 처리 |
|---|---|
| 고치기 | 기존 항목의 내용을 새 내용으로 고친다 (같은 id) |
| 바꾸기 | 기존 항목을 은퇴시키고 새 항목을 등록한다 |
| 따로 두기 | 다른 항목이라는 이유를 적고 새로 등록한다 |

결정 없이 남은 등록은 `heka pending`으로 본다. 등록 자체를 거절하지 않는 이유는 교정이 사라지지 않게 하기 위해서다.

## 4. 기술 구조

```
 AI 도구 (Claude Code, Codex …)
     │ 이벤트                    ▲ 주입문
     ▼                           │
 ┌────────┐   순간   ┌────────┐  │
 │ 연결부 │ ───────▶ │ 선별기 │ ─┘
 └────────┘          └────────┘
                      │읽기  │기록
                      ▼      ▼
 항목 파일 ──색인──▶ 색인   원장 ──▶ 재현기 · 보고
   ▲
   └── 등록 (AI의 조회 도구, 명령줄, 사람의 직접 편집)
```

- **실행 형태**: Go 실행 파일 하나. 훅, 조회 서버, 명령줄이 같은 파일의 하위 명령이다. heka가 따로 띄워 두는 서버는 없다. 조회 서버(`heka mcp`)만 AI 도구가 세션 동안 띄워 둔다(4.5).
- **연결부**: 도구마다 하나씩 둔다. Claude Code 연결부를 먼저 만든다. AI가 직접 부르는 조회·등록은 MCP 서버로 낸다.
- **색인**: 항목 파일에서 만든 파일 하나. 쓰기 경로가 색인을 같은 호출 안에서 갱신하므로 등록 직후 주입된다.
- **원장**: 추가만 하는 줄 단위 파일. 집계는 읽을 때 계산한다.
- **데이터 위치**: 항목, 설정, 원장은 저장소 밖 `$HEKA_HOME`에 둔다. 사용자·조직마다 다른 값(저장소→범위 표 등)은 전부 설정 파일에 있고 코드 기본값은 비어 있다.
- **실패 처리**: 훅은 시간 상한 안에 답하지 못하면 아무것도 넣지 않고 끝낸다. `confirm` 항목도 같다. 어떤 경우에도 막아야 하는 행동(절대 금지)은 heka가 아니라 각 AI 도구의 권한 설정에 둔다(2026-11-13 결정).

### 4.1 색인의 내부

마크다운 파일만으로는 훅 한 번에 수백 개 파일을 읽고 해석해야 하므로 판정에 쓸 수 없다. 항목 파일과 설정 파일을 읽어 검증하고 엮은 색인 파일 하나를 둔다. 색인은 SQLite 파일이다(2026-11-13 결정, 4.7의 실측 참고). 데이터베이스 서버가 아니라 heka가 직접 여는 파일이고, 만들 때마다 임시 파일에 쓴 뒤 이름을 바꿔 통째로 교체한다. 그 안에 네 가지 조회 구조가 표로 들어간다.

| 구조 | 조회 | 쓰는 순간 |
|---|---|---|
| 조건표 | 동작 이름 → `when`이 걸린 항목 | 도구 호출 직전, 세션 시작 |
| 주제어 사전 | 글에 든 주제어 → `about`에 그 말이 있는 항목 | 프롬프트, 서브에이전트 시작 |
| 어휘 색인 | 단어와 두 글자 조각 → 항목, 단어별 희소도 | 프롬프트, 조회 |
| 항목표 | id → 주입문, 출처, 확인 여부, 기한 | 모든 순간 |

설정 파일의 범위 표와 동작 분류가 작은 고정 어휘다. 범위는 포함 관계를 가지고(저장소 ⊂ 팀 ⊂ 조직), 동작도 포함 관계를 가진다(`git.push.force` ⊂ `git.push` ⊂ `git.write`). 상위에 건 조건은 하위에도 걸리고, 하위에 건 조건은 상위 동작만으로는 걸리지 않는다. 강제 푸시에만 해당하는 규칙은 `git.push`가 아니라 `git.push.force`에 건다. 동작마다 그 동작을 시키는 표현을 적은 동작 낱말 사전(3.3)도 설정 파일에 있고, 색인에 함께 실린다.

### 4.2 훅 한 번의 처리

훅은 매번 새 프로세스로 뜨고, 색인 파일을 읽고, 판정하고, 끝난다.

```
도구 호출 직전:   도구 호출 → 동작 해석 → 범위·자격 → 조건표 조회 → 주입문
프롬프트 (동작):  프롬프트 → 동작 낱말 사전 → 시킨 동작 → 범위·자격 → 조건표 조회 → 주입문, 허용 기록
프롬프트 (주제):  프롬프트 → 조각내기 → 범위·자격 → 주제어 사전·어휘 판정 → 주입 또는 침묵
공통:             세션 상태로 중복 제거 → 예산 → 원장에 한 줄 → 출력
```

- 도구 호출 순간은 글의 표현과 무관하게 동작 이름으로 찾는다.
- 프롬프트 순간은 두 갈래다. 동작 조건이 붙은 항목은 동작 낱말 사전이 알아챈 동작으로만 찾고, 그 밖의 항목은 주제어와 어휘로 찾는다(3.2).
- 도구가 만들어 넣은 프롬프트는 두 갈래를 모두 건너뛴다(2.2).
- 주제 갈래는 조사가 붙은 한국어를 잡기 위해 어절과 두 글자 조각을 함께 쓰고, 흔한 단어는 희소도로 눌러 우연한 겹침을 걸러낸다. 글 길이로 정규화한 값이 문턱을 못 넘으면 아무것도 넣지 않는다.

### 4.3 기술별 판단

| 기술 | 푸는 문제 | 드는 것 | 판단 |
|---|---|---|---|
| 조건표 | 행동 규칙이 프롬프트 단어에 의존하던 문제 | 셸 명령을 동작 이름으로 바꾸는 해석기 | 채택 |
| 동작 낱말 사전 | 행동 규칙이 프롬프트의 낱말에 우연히 걸려 생기는 잡음 | 동작마다 표현을 적는 일. 사전에 없는 표현은 프롬프트에서 놓치고 도구 호출 직전에야 준다 | 채택 |
| 주제어 사전 | 흔한 단어가 우연히 겹쳐 생기는 잡음 | 항목마다 주제어를 적는 일 | 채택 |
| 어휘 색인 | 주제어를 빠뜨린 항목 | 두 글자 조각은 heka가 만들고, 찾기는 SQLite의 전문 검색에 맡긴다 | 채택 |
| 고정 어휘 | 범위 누출, 같은 규칙의 중복 작성 | 설정 파일 | 채택 |
| 임베딩 | 표현이 다른데 뜻이 같은 경우 | 프롬프트마다 모델 호출. 로컬에 모델을 띄워 두어야 하고 지연이 붙는다 | 보류 |
| 작은 언어 모델의 판정 | 낱말은 겹치는데 관련이 없는 경우, 표현이 다른데 뜻이 같은 경우 | 프롬프트마다 모델 호출. 네트워크 왕복과 인증이 필요하고 결과가 매번 같지 않을 수 있다 | 보류 |
| 형태소 분석 | 두 글자 조각이 만드는 우연한 일치 | 사전을 품은 분석기. Go만으로 된 한국어 분석기는 성숙도가 낮다 | 보류 |
| SQLite 파일 | 색인 엔진을 직접 만들지 않아도 된다. 원장을 임의로 질의할 수 있다 | 의존 모듈 하나, 실행 파일 약 4MB 증가 | 채택 |
| 벡터 DB | 수십만 건 이상에서의 근사 검색 | 별도 저장소와 운영 | 기각 |
| 지식 그래프 | 여러 단계 추론, 시간에 따른 사실 변화 | 엔터티 추출, 동일성 판정, 검수 | 기각 |

동작 낱말 사전을 넣은 근거는 재현 세트의 비교다(2026-11-13). 기존 heka가 프롬프트 시점에 넣었던 사례 가운데 사람이 확인한 29건(넣어야 함 10, 넣지 말아야 함 19)으로 견줬다.

| 방식 | 넣어야 할 10건 중 넣음 | 넣지 말아야 할 19건 중 거름 |
|---|---|---|
| 기존 heka | 10 | 0 |
| 주제어 일치만 | 0 | 18 |
| 작은 언어 모델에 한 건씩 묻기 | 7 (다시 돌리면 5) | 17 (다시 돌리면 18) |
| 동작 낱말 사전과 주제어 일치 | 6 | 18 |

- 넣지 말아야 할 19건 중 13건이 동작 조건이 붙은 항목이었다. 기존 잡음의 큰 몫이 행동 규칙을 프롬프트의 낱말로 찾은 데서 나왔다.
- 사전과 모델은 이 자료로 구분되지 않는다. 넣어야 할 사례가 10건뿐이고, 사전은 사례 일부를 본 뒤에 적었고, 모델은 하나를 지시문 하나로 잰 값이다.
- 프롬프트에서 놓친 것을 도구 호출 직전에 주는 길이 실제로 메우는지는 구현 뒤에 잰다.

뜻의 신호(임베딩이나 작은 언어 모델의 판정)를 넣을지는 정해지지 않았다. 넣지 않는 것이 기본이고, 재현 결과에서 필요가 확인될 때 고른다. 아래는 임베딩을 넣는다면 어떤 모습일지 적어 둔 것이다.

- 조각내기와 임베딩은 맡는 문제가 다르다. 낱말 경계 문제(조사, 두 글자 낱말, 띄어쓰기)는 조각내기가 맡는다(4.4). 모델이 필요 없고 비용이 거의 없다. 임베딩은 조각내기로 풀 수 없는 것, 곧 말은 다른데 뜻이 같은 경우를 맡는다.
- 로컬 전용이다. 프롬프트를 외부로 보내지 않는다. 로컬 임베딩 모델이 떠 있을 때만 쓰고, 없거나 시간 안에 답하지 않으면 어휘 신호만으로 판정한다.
- 항목의 임베딩은 색인을 만들 때 계산해 색인 파일의 다섯 번째 구조로 둔다. 훅이 부르는 것은 프롬프트 한 건의 임베딩뿐이다. 수천 건은 전수 비교로 충분해 벡터 DB는 쓰지 않는다.
- 쓰는 곳은 프롬프트 순간과 조회다. 도구 호출 순간은 동작 이름으로 찾으므로 쓰지 않는다.
- 기본으로 켤지와 문턱은 재현 결과로 정한다.

### 4.4 한국어를 다루는 법

| 문제 | 예 | 대응 |
|---|---|---|
| 조사와 어미가 붙는다 | "커밋 메시지를", "푸시하면" | 주제어는 어절의 앞부분과 견준다 |
| 두 글자 낱말이 많다 | "견적", "결제" | 세 글자가 아니라 두 글자 조각으로 색인한다 |
| 띄어쓰기가 흔들린다 | "커밋메시지", "커밋 메시지" | 주제어는 공백을 지운 형태로도 견준다 |
| 뜻은 같은데 말이 다르다 | "삭제", "지워", "remove" | 글자 처리로는 풀 수 없다. 주제어에 다른 표현을 함께 적는다. 그래도 부족한지는 재현 결과로 본다 |
| 필수 규칙 | "요청 없이 푸시하지 않는다" | 글의 낱말이 아니라 동작으로 찾는다. 도구 호출은 동작 이름으로, 프롬프트는 동작 낱말 사전으로 알아챈다 (3.3) |

### 4.5 프로세스와 파일

서버도 데이터베이스 프로세스도 없다. 실행 파일 하나가 세 가지 방식으로 불린다.

| 진입점 | 누가 부르는가 | 수명 | 건드리는 파일 |
|---|---|---|---|
| `heka hook` | AI 도구의 훅 | 이벤트마다 떴다 끝난다 | 색인 읽기, 세션 상태 읽기·쓰기, 원장 줄 추가 |
| `heka mcp` | AI 도구 (조회·등록) | 세션 동안 떠 있다 | 색인 읽기, 항목 쓰기 후 색인 교체 |
| `heka add·why·replay` | 사람 | 부를 때만 | 항목 쓰기, 원장·재현 세트 읽기 |

세션이 여럿이면 훅 프로세스가 동시에 여러 개 뜬다. 색인은 이름 바꾸기로 한 번에 교체하고 원장은 줄 단위로 덧붙이므로 서로 깨뜨리지 않는다. 항목 파일을 사람이 직접 고치면 다음 훅이 색인이 낡은 것을 알아채 다시 만든다.

### 4.6 훅과 MCP의 역할

둘 다 모델의 컨텍스트에 글을 넣는다. 다른 점은 누가 시작하느냐다. 빠뜨리면 안 되는 것은 훅이 맡고, 훅이 미리 알 수 없는 필요는 MCP가 맡는다.

| | `heka hook` | `heka mcp` |
|---|---|---|
| 누가 시작하나 | AI 도구의 하네스 | 모델 |
| 입력 | 이벤트: 프롬프트 글, 도구 호출 | 모델이 쓴 질의, 등록할 내용 |
| 하는 일 | 확신 있는 것만 짧게 넣는다 | 배경을 읽는다. 교정을 등록한다. 틀린 항목을 표시한다 |
| 약점 | 미리 정한 순간과 조건 밖의 필요는 못 채운다 | 부르지 않으면 없다 |
| 훅이 없는 AI 도구 | 쓸 수 없다 | 유일한 경로가 된다 |

- MCP의 조회는 별도 조립기를 두지 않고 같은 선별기를 넉넉한 예산으로 돌린다.
- MCP가 돌려준 항목도 원장에 남긴다. 같은 실행 파일이므로 이를 관찰하는 별도 훅이 필요 없다.
- 기존 heka의 두 달 실적은 훅 판정 9,574회, MCP 호출 1,301회였다. 서브에이전트 74개 중 스스로 조회한 것은 11개였다. 서브에이전트에게는 밀어 넣기가 사실상 유일한 전달 경로다.

### 4.7 색인 방식 실측 (2026-11-13)

훅은 이벤트마다 새 프로세스로 뜨므로, 색인을 여는 비용이 매번 든다. 두 방식을 같은 조회 세 가지(조건표, 주제어 사전, 어휘 색인)로 쟀다.

| | 직접 만든 파일 | SQLite 파일 |
|---|---|---|
| 훅 1회, 항목 500건 | 10.2ms (95%는 12.6ms 이내) | 11.2ms (95%는 21.5ms 이내) |
| 훅 1회, 항목 5,000건 | 20.1ms (95%는 22.8ms 이내) | 13.4ms (95%는 15.0ms 이내) |
| 색인을 여는 시간, 500건 → 5,000건 | 1.1ms → 8.1ms | 0.4ms → 0.4ms |
| 읽는 도중 색인 교체, 800회 실행 | 실패 0 | 실패 0 |
| 실행 파일 크기 | 2.1MB | 6.5MB |

- 아무 일도 하지 않는 프로세스가 뜨고 끝나는 데 7.2ms가 든다.
- 두 방식 모두 목표(S5, 50ms) 안이다. 속도로는 갈리지 않는다.
- SQLite 파일로 정한 이유: 색인 엔진을 직접 만들지 않아도 되고, 항목이 늘어도 여는 시간이 같고, 원장을 SQL로 질의할 수 있다.
- 함께 확인한 것: cgo 없이 Go만으로 된 SQLite 드라이버에서 전문 검색(FTS5)과 단어별 문서 수 조회가 동작한다. 세 글자 조각 방식은 두 글자 검색어를 찾지 못한다. 그래서 두 글자 조각은 heka가 직접 만들어 넣는다.
- 조건: Go 1.27, arm64 macOS, `modernc.org/sqlite` v1.62.0(SQLite 3.54.1), 프로세스 200회 순차 실행.
- 한계: 지어낸 데이터로 한 번 잰 값이고 디스크 캐시가 데워진 상태였다. 검색 품질은 재지 않았다. SQLite 500건에서 95% 값이 튄 원인은 조사하지 않았다.

### 4.8 파일 배치

```
$HEKA_HOME/
  items/*.md             정본. git으로 이력 관리
  items/_pending/*.md    대기함. 결정을 기다리는 등록. 주입하지 않는다
  config.yaml            범위 표, 동작 분류, 동작 낱말 사전, 순간별 예산
  index/index.db         색인(SQLite 파일). 지우고 다시 만들 수 있다
  ledger/2026-11.jsonl   원장. 추가만 한다
  sessions/<id>.json     세션 상태. 이미 넣은 항목 목록
  replay/                재현 세트. 실제 데이터라 저장소에 넣지 않는다
```

가장 큰 복잡도는 "도구 호출을 동작 이름으로 바꾸는 일"에 있다. 셸 명령은 같은 동작을 여러 방식으로 쓸 수 있어서다. 이 부분의 크기도 5장의 크기 기준(S7)에 포함해 잰다.

### 4.9 바깥 과정을 위한 창구

교훈을 에이전트 정의·스킬·검사로 옮기는 과정은 heka 밖에서 돈다(2.5). heka는 그 과정이 쓸 명령만 낸다.

| 명령 | 내는 것 |
|---|---|
| `heka list --json` | 항목 목록. `--agent <종류>`는 그 에이전트에만 걸린 항목, `--violated <횟수>`는 전달된 뒤 그 횟수 이상 어겨진 항목 |
| `heka stats <id> --json` | 그 항목의 주입 횟수, 어겨진 횟수, 마지막 주입 시각 |
| `heka retire <id> --reason <글>` | 항목을 은퇴시킨다. 파일을 지우고 사유를 git 커밋에 남긴다. 이력은 git에 있다 |

"어겨진 횟수"는 heka가 스스로 셀 수 있는 것만 센다: 결과물 검사에 걸린 횟수와, 사용자가 피드백 명령으로 표시한 횟수다. 글을 읽고 위반을 판정하는 일은 heka가 하지 않는다.

## 5. 성공 조건

숫자는 모두 제안이다. 재현 세트는 기존 heka의 원장과 과거 세션에서 만들되, 실제 데이터는 저장소 밖에 둔다.

| # | 조건 | 재는 법 | 합격선 (제안) |
|---|---|---|---|
| S1 | 전달률 | 재현 세트에서, 알았어야 할 항목이 행동 전에 주입된 비율 | 필수 100%, 전체 90% 이상 |
| S2 | 정밀도 | 실제 프롬프트 표본에서, 주입된 항목 중 관련 있는 비율 | 70% 이상 |
| S3 | 침묵 | 무관한 프롬프트 세트에서 아무것도 넣지 않은 비율 | 95% 이상 |
| S4 | 준수 | 주입된 필수 항목이 그 세션에서 위반된 비율 | 기준선을 먼저 잰 뒤 정함 |
| S5 | 속도 | 훅 1회 응답 시간, 등록 후 반영 시간 | 95%가 50ms 이내, 반영은 즉시 |
| S6 | 토큰 | 순간별 주입 토큰 | 세션 시작 1,000 이하, 그 외 300 이하 |
| S7 | 크기 | 테스트를 뺀 코드 줄 수, 직접 의존 모듈 수 | 5,000줄 이하, 3개 이하 |
| S8 | 설명 가능 | 임의의 주입에 대해 이유를 한 명령으로 확인. 사용자가 구조를 직접 설명 | 둘 다 가능 |
| S9 | 실사용 | 2주 사용 중 "등록돼 있었는데 또 지적한" 건수 | 기존 heka보다 적음 |
| S10 | 불필요한 확인 | 사용자가 그 턴에 시킨 일인데 확인을 요구한 횟수 | 0 |

S1~S3과 S5~S7은 재현기로 자동 측정한다. S4, S9, S10은 실사용 기록이 필요하다.

조건끼리 충돌하면 반복 실수 감소(S1~S4, S9)가 우선이다(2026-11-13 결정). 속도·토큰·크기는 합격선을 넘는지만 본다.

### 합격선 예시와 기존 heka의 기준선

합격선은 두 단계로 둔다. 최소 합격선에 못 미치면 교체하지 않고, 목표에 닿으면 충분하다고 본다. 아래 숫자는 예시이며 확정 전이다. 기준선은 기존 heka의 두 달 기록에서 센 것이다.

| # | 기존 heka의 기준선 | 최소 합격선 (예시) | 목표 (예시) |
|---|---|---|---|
| S1 전달률 | 규칙이 있었던 사건 21건 중 전달된 것 13건 (62%). 사건만 센 값이다 | 필수 95%, 전체 80% | 필수 100%, 전체 90% |
| S2 정밀도 | 22% (사후 판정 54건 중 12건) | 50% | 70% |
| S3 침묵 | 무관한 질문 15개 중 14개 (93%), 헷갈리는 질문 20개 중 15개 (75%). 평가 문항으로 잰 값이다 | 90% | 95% |
| S4 준수 | 비율은 재지 못했다. 한 달 사건 23건 중 전달됐는데 어긴 것이 12건 | 같은 기간 건수가 늘지 않음 | 절반 이하 |
| S5 속도 | 190~260ms (다른 언어로 된 훅, 프로세스 기동 포함) | 95%가 100ms 이내 | 95%가 50ms 이내 |
| S6 토큰 | 세션 시작 평균 336, 프롬프트 주입 평균 158(최대 300), 도구 호출 안내 평균 266(최대 657), 세션당 합계 평균 1,279 | 세션 시작 1,000, 그 외 1회 300 | 세션당 합계 1,300 이하 |
| S7 크기 | 약 18,500줄 (웹 화면 제외) | 8,000줄 | 5,000줄 |
| S9 실사용 | 40세션을 감사해 사건 19건 | 같은 방식으로 절반 이하 | 4분의 1 이하 |
| S10 불필요한 확인 | 재지 못했다 | 2주에 2회 이하 | 0 |

- S8은 숫자가 아니라 되는지 안 되는지로 본다.
- 실측한 Go 방식의 훅은 10~20ms였다(4.7). S5의 목표는 여유가 있다.
- 확정은 재현 세트로 기존 heka를 먼저 잰 뒤에 한다. 위 기준선 가운데 S1과 S3은 재는 방식이 달라서 그대로 비교할 수 없다.

### 재현 세트

재현 세트는 이미 판정된 자료에서 만든다(2026-11-13 결정): 주입을 사후 판정한 것, 반복 실수로 기록된 사건, 평가 문항이다. 후보 목록을 만들고 사용자가 채택 여부를 판단한다. 기존 판정이 불명확하거나 사용자가 쓴 프롬프트가 아닐 수 있어 주의 표시가 붙은 후보는 사용자가 모두 본다. 표시가 없는 후보는 기존 판정대로 넣되 사람이 확인하지 않은 것으로 적고 점수를 따로 낸다. 새 구조에 대상 항목이 없어 잴 수 없는 후보는 뺀다. 실제 데이터이므로 저장소에 넣지 않는다.

기존 설계 점검표에 대한 판단은 다음과 같다.

| 점검 항목 | 판단 | 이유 |
|---|---|---|
| 관련도와 신뢰의 분리 | 채택 | 3.2 |
| 컨텍스트 조립 규칙 | 채택 | 본체다 |
| 평가 범주 (적중·침묵·범위 누출·낡음) | 채택 | S1~S3과 재현 세트의 범주 |
| 유효 시간과 기록 시간의 이중 질의 | 기각 | `expires`와 git 이력으로 대신한다. 과거 시점 질의는 원장이 당시 주입문을 보관한다 |
| 원천 버전 보존 | 기각 | 2.3 |
| 행동용 절차 형식 | 기각 | 절차는 각 AI 도구의 스킬이 맡고, heka는 그 스킬을 쓰라는 항목만 주입한다 |

## 6. 기존 heka에서 가져오는 것과 두고 오는 것

두 달 동안 실제로 쓰인 것은 가져오고, 만들어 놓았지만 쓰이지 않은 것은 두고 온다. 숫자는 기존 heka의 기록에서 센 것이다.

| 가져오는 것 | 이유 | 실적 |
|---|---|---|
| 셸 명령을 동작 이름으로 바꾸는 해석기와 시험 사례 | 가장 복잡한 부분이 이미 Go로 있고 실제 명령 변형을 겪었다 | 판정 6,582회 |
| 줄 단위 원장과 파일 잠금 | 데이터베이스 없이 여러 세션의 동시 실행을 견딘 방식이다 | 약 11,000줄 |
| 말로 한 허용 | "푸시해 줘"를 그 턴의 허락으로 본다. 없으면 시킨 일에도 확인 창이 뜬다 | 91건 |
| 결과물 검사 | 커밋 메시지, PR 본문, 마지막 응답을 정해 둔 형식과 견준다 | 미확인 |
| 등록할 때 비슷한 항목 확인 | 중복과 충돌을 등록 시점에 막는다 | 미확인 |
| 사건 분류와 쌓인 자료 | 사건 36건, 주입 판정 54건, 평가 문항 91개가 재현 세트의 씨앗이 된다 | 181건 |
| 모델을 거치지 않는 피드백 명령 | 사용자가 "이 항목 틀렸다"를 바로 남긴다 | 3건 |

| 바꿔서 가져오는 것 | 어떻게 | 실적 |
|---|---|---|
| 개정 이력 | 별도 표 대신 git에 맡긴다. 원장에 항목의 내용 해시를 남겨 당시 주입문을 되찾는다 | 개정 889건 |
| 작업용 컨텍스트 묶음 | 별도 조립기 대신 같은 선별기를 넉넉한 예산으로 돌린다 | 132회 |

| 두고 오는 것 | 쓰인 정도 |
|---|---|
| 과거 시점으로 묻기 | 컨텍스트 조회 221회 가운데 과거 시점을 물은 것은 0회 |
| 구조화한 주장과 충돌 감지 | 주장 3건, 감지된 충돌 0건 |
| 근거의 원문 위치 | 근거가 붙은 항목 2건 |
| 관계 그래프 | 관계 580건 중 455건이 단순 "관련"이고 주입 판정에는 쓰이지 않았다 |

말로 한 허용, 결과물 검사, 등록할 때 비슷한 항목 확인은 처음 설계에 빠져 있었고, 2026-11-13에 넣기로 정했다(3.3, 3.4).

| 전달돼도 어긴다 | 2026년 11월 사건 23건 중 12건 | 본문을 직접 주고, 검사할 수 있는 것은 결과물 검사로 잡는다. 태도에 관한 규칙은 여전히 못 잡는다 |

| 사전에 없는 표현은 프롬프트에서 놓친다 | 사람이 확인한 사례에서 넣어야 할 10건 중 4건을 놓쳤다: 사전에 없는 표현 2건, 규칙을 묻는 말 1건, 도구가 만든 프롬프트 1건 | 행동이 따르면 도구 호출 직전에 준다. 구현 뒤 재현으로 잰다. 사전은 설정 파일이라 사용자의 표현을 더할 수 있다 |
