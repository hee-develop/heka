# heka2 설계

> 상태: 설계와 첫 구현. 마지막으로 고친 날은 2026-11-16이다. 훅, 조회·등록, MCP 서버, 결과물 검사, 그림자 방식, 재현기가 구현돼 있다. 범위·개입 수준·등록 자격·우선순위는 정해졌다. "제안"이나 "잠정"이라고 적힌 것과 7장의 열린 결정은 확정이 아니다.
> 논의 경과는 저장소에 올리지 않는 로컬 기록에 남긴다. 이 문서의 예시는 전부 지어낸 것이다.

## 1. 정의와 원칙

**heka는 AI 에이전트가 일하는 각 순간에, 그 순간에 필요한 컨텍스트만 골라 행동 전에 전달하고, 그 전달이 맞았는지 기록으로 확인하는 개인용 컨텍스트 주입기다.**

본체는 주입이다. 저장·검수 같은 관리 기능은 주입 품질을 올리는 데 필요한 만큼만 둔다.

원칙은 여섯 가지다.

1. **주입이 본체, 관리는 보조.** 어떤 기능이든 "이것이 주입을 더 정확하게 만드는가"로 넣을지 정한다.
2. **확신이 없으면 침묵한다.** 무관한 주입은 주입이 없는 것보다 나쁘다. 주입 줄 전체를 믿지 않게 만든다.
3. **주입문만 읽고 행동할 수 있어야 한다.** 제목을 주고 본문을 찾아 읽게 하지 않는다.
4. **모든 주입은 설명할 수 있어야 한다.** 무엇을, 어떤 조건이 맞아서 넣었는지 한 줄로 남긴다.
5. **사람이 읽는 파일이 정본이다.** 그 밖의 것은 지우고 다시 만들 수 있다.
6. **작게 만든다.** 한 화면 도식으로 설명할 수 없는 구성 요소는 넣지 않는다.

구성 요소는 다섯 개다.

| 구성 요소 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 항목 파일 | 주입 단위 하나를 마크다운 파일 하나로 보관한다 | 원문 사본 저장 |
| 선별기 | "지금 이 순간"을 받아 넣을 항목과 형태를 정한다 | 클라이언트 형식 해석 |
| 연결부 | 클라이언트의 이벤트를 선별기 입력으로, 선별 결과를 클라이언트 출력으로 바꾼다 | 무엇을 넣을지 판단 |
| 원장 | 훅 한 번의 판단(넣은 항목과 이유, 탈락과 단계, 동작, 확인, 검사, 토큰)과 조회·등록·표시·은퇴 같은 사건을 한 줄씩 기록한다 (4.11) | 판단에 개입 |
| 재현기 | 기록된 순간을 선별기에 다시 넣어 성공 조건을 잰다(`heka replay`). 원장과 세션 상태는 쓰지 않는다 | 실사용 경로에 개입 |

## 2. 해야 하는 일

### 2.1 요구사항

| # | 요구 | 풀려는 문제 |
|---|---|---|
| R1 | 정해진 순간마다 주입한다(2.2) | 지적한 것이 반복됨 |
| R2 | 관련 있는 것만 넣고, 확신이 없으면 넣지 않는다 | 지적한 것이 반복됨 |
| R3 | 주입문은 그대로 행동 지침이 된다 | 전달됐는데 지키지 않음 |
| R4 | 주입마다 내용·이유·시각을 기록하고 한 명령으로 조회한다 | 무엇을 하는지 안 보임 |
| R5 | 주입되는 항목마다 출처, 사람 확인 여부, 유효기한을 가진다 | 내용을 믿기 어려움 |
| R6 | 사용자의 교정은 등록된 직후부터 주입 대상이 된다 | 지적한 것이 반복됨 |
| R7 | 선별기는 어떤 AI 도구인지 모른다 | 플랫폼 종속 |
| R8 | 항목은 사람이 편집기로 읽고 고칠 수 있다 | 내용을 믿기 어려움 |
| R9 | heka가 실패해도 작업은 계속된다 | 단일 장애점 |
| R10 | 전체 구조를 사용자가 직접 설명할 수 있는 크기로 유지한다 | 너무 크고 이해가 안 됨 |
| R11 | 기계가 검사할 수 있는 규칙은 결과물을 직접 검사한다 | 전달됐는데 지키지 않음 |
| R12 | 사용자가 그 턴에 시킨 일에는 확인을 다시 묻지 않는다 | 불필요한 확인 |
| R13 | 비슷한 항목이 이미 있으면 등록 전에 결정을 받는다 | 내용을 믿기 어려움 |

### 2.2 주입하는 순간

| 순간 | 선별기가 받는 것 | 넣는 것 |
|---|---|---|
| 세션 시작, 압축 직후 | 작업 위치 | 그 범위에서 `when.moment`에 세션 시작이 적힌 항목. 동작 조건이 걸린 필수 항목은 여기서 넣지 않고 그 동작의 도구 호출 직전에 넣는다 |
| 사용자 프롬프트 | 프롬프트 글 | 프롬프트가 묻거나 시키는 것에 답이 되는 참고 항목(최대 3건)과, 프롬프트가 시킨 동작에 조건이 걸린 필수 항목 (3.2) |
| 도구 호출 직전 | 동작 이름, 대상 경로, 명령 | 조건이 일치하는 필수 항목 본문 |
| 서브에이전트 시작 | 에이전트 종류, 위임 글 (4.2) | 범위에서 `when.moment`에 서브에이전트 시작이 적힌 항목과 `when.agent`가 그 종류인 항목. 동작 조건이 걸린 필수 항목은 도구 호출 직전에 넣는다. 참고 항목은 위임 글로 프롬프트 순간과 같은 방식으로 고른다 (7장 8번) |
| AI 또는 사람의 조회 | 질의(낱말 나열이나 작업을 설명하는 문장) | 검색된 항목의 주입문과 본문 (4.6) |
| 턴 종료 | 마지막 응답 | 넣지 않는다. 결과물 검사에 걸렸을 때만 사유를 돌려준다 (3.3) |

도구가 만들어 넣은 프롬프트(하위 에이전트의 완료 알림 등)는 프롬프트 순간으로 보지 않는다(2026-11-13 결정). 그 글로 항목을 찾지 않고, 말로 한 허용도 읽지 않는다. 사용자의 지시가 아니고, 글이 길어 주제어가 우연히 겹치기 쉽기 때문이다. 사용자가 쓴 프롬프트인지는 연결부가 가린다.

### 2.3 하지 않는 일

이 설계에서는 아래를 만들지 않는다(2026-11-13 결정). 주입에 직접 기여하지 않거나, 기존 heka에서 사용 실적이 거의 없었다. 지식은 대화 중 등록과 사람의 직접 편집으로만 들어온다.

- 외부 문서·메신저·이슈 추적기의 원문 수집과 사본 보관
- LLM이 밤에 도는 자동 추출·판정·정리 작업
- 웹 화면, 그래프, 묶음(컬렉션), 절차 실행기
- 임베딩 검색과 벡터 DB (뜻의 신호는 작은 언어 모델의 판정으로 낸다. 4.3)

### 2.4 heka에 넣는 것과 넣지 않는 것

기준은 하나다. 지식이 에이전트를 따라다니면 에이전트 정의에 두고, 상황(어느 저장소인지, 어떤 동작인지, 누구의 일인지)을 따라다니면 heka에 둔다.

| 넣는 것 | 예 | 주입 |
|---|---|---|
| 규칙·선호 | 커밋 메시지는 한국어로 쓴다 | 필수, 동작 조건 |
| 용어·사실 | 여기서 "주문"은 결제가 끝난 건만 뜻한다 | 참고, 주제어 |
| 결정과 이유 | 색인은 다시 만들 수 있는 파일로 둔다 | 참고, 프로젝트 범위 |
| 진행 상태 | 결제 화면 개편은 2단계까지 끝났다 | 참고, 기한 필수 |
| 가리키는 말 | PR은 전용 스킬로 만든다 | 필수 또는 참고 |

| 넣지 않는 것 | 대신 두는 곳 |
|---|---|
| 에이전트의 역할과 완료 기준 | 에이전트 정의 |
| 여러 단계의 절차 | 스킬 |
| 기계가 검사할 수 있는 규칙의 집행 | 린트, 테스트, 훅의 결과물 검사 |
| 코드에서 읽을 수 있는 것 | 저장소 |
| 문서 원문 | 원래 있던 곳. heka에는 링크만 |

### 2.5 교훈을 두는 자리

에이전트가 실수했을 때 교훈을 어디에 둘지는 위에서부터 묻는다. 위쪽일수록 지켜질 보장이 강하다.

```
0. 먼저 원장에 사건으로 남긴다 (항상)
1. 기계가 잡아낼 수 있는가            → 검사로 만든다 (린트·테스트·훅의 결과물 검사)
2. 그 에이전트라면 어디서든 해당하는가  → 에이전트 정의를 고친다
3. 특정 저장소·팀·사람의 사정인가      → heka 항목으로 등록한다
4. 여러 단계로 된 방법인가            → 스킬로 만든다. heka에는 그 스킬을 쓰라는 한 줄만
5. 고친 뒤에는 그 상황을 재현 세트에 넣는다
```

- 내장 에이전트나 남이 만든 에이전트처럼 정의를 고칠 수 없으면 2를 건너뛰고 heka가 맡는다.
- heka 항목이 전달됐는데도 거듭 어겨지면 원장에 드러난다. 그 항목은 검사나 에이전트 정의로 올린다.
- 운영 방식(2026-11-13 결정): 교훈은 일단 heka에 받는다. 위 순서에 따라 에이전트 정의·스킬·검사로 옮기는 일은 heka와 무관하게 도는 별도 과정이 주기적으로 한다. heka는 그 과정이 쓸 창구만 낸다(4.9).

## 3. 개념 모델

### 3.1 항목

주입 단위 하나가 파일 하나다.

```markdown
---
id: commit-message-language
text: 커밋 메시지는 한국어로 쓰고 첫 줄은 50자 이내로 한다.
must: true
when:
  action: git.commit
about: [커밋 메시지, commit message]
scope: [repo/sample-app]
source: user
quote: "커밋 메시지는 한국어로 써 줘. 첫 줄은 짧게."
checked: 2026-11-13
expires:
confirm: false
---
배경과 예시. 조회할 때만 읽힌다.
```

| 필드 | 뜻 |
|---|---|
| `text` | 주입문. 한두 문장이고 이것만 읽어도 행동할 수 있어야 한다 |
| `must` | 반드시 지킬 것인가(true), 알면 좋은 것인가(false) |
| `when` | 구조로 판정하는 조건: 순간(`moment`: session_start, prompt, tool, subagent_start), 동작(`action`), 경로(`path`), 저장소(`repo`), 에이전트 종류(`agent`). `agent`의 `main`은 서브에이전트가 아닌 본체를 가리킨다. 본체에만 줄 항목(예: 서브에이전트에 위임하라는 규칙)에 쓴다 |
| `about` | 주제어. 프롬프트·위임 글과 견준다. 동작 조건이 붙은 항목에서는 조회에만 쓴다 (3.2) |
| `scope` | 주입해도 되는 범위. 범위 밖에서는 후보에도 들지 않는다 |
| `source` | 누가 말했는가: user, doc, ai |
| `quote` | `source: user`일 때 근거가 되는 사용자 발화. 등록할 때 AI 도구가 저장한 세션 기록에서 사용자가 친 글을 읽어 대조하고, 실제로 있는 말인지 확인한다 (3.4) |
| `checked` | 사람이 확인한 날. 비어 있으면 미확인 |
| `expires` | 유효기한. 지나면 주입하지 않고 점검 목록에 올린다 |
| `confirm` | false(기본)는 알리기만 한다. true는 사용자가 그 턴에 시킨 일이 아니면 확인을 요구한다. always는 시킨 일이어도 매번 확인한다 (3.3) |
| `check` | 선택. 결과물 검사 (3.3) |
| `push` | 없으면 true. false면 조회로만 찾고 heka가 스스로 넣지 않는다. `must: true`, `when`, `confirm: true`·`always`, `check`와 함께 쓸 수 없다 |

같은 id의 내용이 바뀌면 파일을 고친다. 이력은 git이 보관한다.

### 3.2 선별 순서

순서는 고정이고 단계마다 탈락 사유가 원장에 남는다.

```
범위 → 자격 → 일치 → 중복 제거 → 예산 → 형태
```

- 조회 전용 항목(`push: false`)은 어느 순간에도 후보가 아니다. 탈락으로도 남기지 않고 조용히 건너뛴다. 조회(`heka find`)는 평소처럼 찾는다.
- **범위**: 작업 위치로 정한 범위에 속한 항목만 후보가 된다. 범위를 알 수 없으면 전역 항목만 본다.
- **자격**: 기한이 지난 항목은 탈락한다. 사람이 확인한 항목은 통과한다. 미확인 항목은 출처에 따라 다르다.

  | 출처 | 미확인일 때 |
  |---|---|
  | user, 대조된 `quote` 있음 | 통과. 등록 직후부터 주입된다 |
  | user, `quote` 없음 | 탈락 |
  | doc | 참고로만 통과. 필수 항목이 될 수 없다 |
  | ai | 탈락 |
- **일치**: `when`은 구조 비교로 판정한다. 참고 항목은 두 단계로 고른다(2026-11-14 결정).

  1. 후보를 잡는다. 주제어(`about`)가 프롬프트에 든 항목과, 낱말 겹침 점수가 높은 항목 3건이다(후보 범위는 잠정). 점수는 프롬프트와 항목에 함께 있는 낱말 조각의 희소도 합을, 프롬프트 조각 전체의 희소도 합으로 나눈 값(0~1)이다. 흔한 조각일수록 희소도가 낮다(4.1).
  2. 후보마다 작은 언어 모델에게 "이 항목이 프롬프트가 묻거나 시키는 것에 직접 답하는가"를 묻고, 그렇다고 답한 것만 넣는다(4.3).

  주제가 같아도 항목에 답이 없으면 넣지 않는다. 주제어와 낱말은 후보를 잡는 데만 쓰고, 넣을지는 정하지 않는다. 모델이 시간 안에 답하지 않거나 판정 명령이 설정돼 있지 않으면 참고 항목은 넣지 않는다(원칙 2).

  후보를 모델이 항목 목록에서 고르는 갈래를 기록 전용으로 둘 수 있다(`judge.pick.mode: record`). 지금 방식의 후보 잡기·판정과 동시에 돌아, 모델이 고른 항목을 한 건씩 판정한 결과를 원장에만 남긴다. 무엇을 넣을지는 바꾸지 않는다. 프롬프트마다 대상 항목 전체를 모델에 읽히므로 항목 수에 비례해 비용이 들고, 훅 시간이 늘어나므로 그림자 방식(4.10)에서 쓰는 것을 전제로 한다.

  동작 조건이 붙은 항목(행동 규칙)은 프롬프트의 낱말이나 주제어로 찾지 않는다(2026-11-13 결정). 프롬프트가 그 동작을 시키면 동작 낱말 사전(3.3)으로 알아채 미리 주고, 그렇지 않으면 도구 호출 직전에 준다. 이런 항목의 `about`은 조회와, 등록할 때 비슷한 항목을 찾는 데만 쓴다.
- **중복 제거**: 같은 항목은 세션에 한 번만 넣는다. 서브에이전트는 메인과 따로 센다(에이전트마다 따로 적는다). 압축(`compact`)이나 `clear` 뒤의 세션 시작에서는 다시 넣는다. 확인(`confirm`)이나 검사(`check`)가 붙은 항목은 이미 넣었어도 도구 호출 때 다시 판정한다. 허용이 거둬졌거나 `always`일 수 있고, 검사는 넣는 일과 따로 매번 해야 해서다. 글을 또 넣지는 않는다.
- **예산**: 순간별 토큰 상한은 기본으로 두지 않는다(2026-11-16 결정). 상한이 있으면 필수 규칙이 첫 행동 뒤에야 도착하는 것이 실제 세션에서 확인됐다. 넣은 양은 원장에 남기고, 너무 많아지면 설정으로 상한을 건다. 상한을 걸면 넘칠 때 필수 항목을 먼저 남긴다. 참고 항목은 한 번에 3건까지다.
- **형태**: 필수 항목은 `text` 전문, 참고 항목은 `text`와 id.

관련도와 신뢰를 한 점수로 합치지 않는다. 신뢰는 자격 단계에서 걸러내는 데만 쓴다.

### 3.3 행동 시점의 개입

도구 호출 직전에 조건에 걸린 항목은 세 갈래로 처리된다. 세 갈래 모두 원장에 한 줄을 남긴다.

| 항목 | 처리 |
|---|---|
| 알리기만 하는 항목 (`confirm: false`) | 주입문을 넣고 진행한다 |
| 확인을 요구하는 항목 (`confirm: true`) | 사용자가 그 턴에 시킨 일이면 진행하고, 아니면 사용자에게 확인을 요구한다 |
| 검사가 붙은 항목 (`check`) | 결과물이 형식에 맞으면 진행하고, 아니면 막고 사유를 모델에게 돌려준다. 사람에게 묻지 않는다 |

확인을 요구할 때의 허용은 그 동작이나 상위 동작에 있어야 하고, 한 호출이 여러 동작에 걸리면 모든 동작에 있어야 한다.

확인을 요구하는 항목은 되돌릴 수 없는 파괴적 동작에만 둔다(2026-11-15 결정). 푸시나 PR 만들기처럼 자동화의 중간 단계가 되는 동작에는 걸지 않는다. 사람이 자리에 없는 동안 확인 요청 하나가 뒤의 단계를 모두 멈추기 때문이다.

**동작 이름.** 도구 호출은 동작 이름으로 바뀐다. 코드가 내는 이름은 `git.commit`, `git.push`, `git.push.force`, `git.destructive`, `code.edit`, `doc.edit`, `agent.delegate`, `skill.run` 등이고, 도구 이름이나 스킬 이름으로만 알 수 있는 동작은 설정의 `tool_actions`로 잇는다. PR은 `pr.create`와 `pr.edit`(`gh pr create`·`gh pr edit`, `gh api`로 PR을 만들거나 고치는 호출)로 나뉘고, 예시 설정은 둘의 상위 동작 `pr.write`를 둔다. PR 본문에 관한 규칙은 `pr.write`에 걸면 둘 다 걸린다.

**동작 낱말 사전.** 프롬프트가 어떤 동작을 시키는지는 동작별 표현을 적은 사전 하나로 알아챈다("푸시해 줘" → `git.push`). 사전은 두 곳에 쓰인다(2026-11-13 결정).

- 미리 주기: 프롬프트가 시킨 동작에 조건이 걸린 필수 항목을 프롬프트 순간에 준다. 사전이 알아채지 못하면 도구 호출 직전에 준다.
- 말로 한 허용: 그 동작의 허용을 세션 상태에 적는다.

부정("하지 마"), 질문("해도 돼?"), 조건("하기 전에")이 섞이면 시킨 것으로 보지 않는다. 표현이 맞은 자리 뒤 몇 글자(`negation_window`)까지 부정·질문·조건 표현(`negations`)이 있으면 그 자리는 버리고, 모든 자리가 버려진 동작은 "거절"로 원장에 남긴다. 사전은 설정 파일에 둔다. 저장소에는 한국어와 영어의 최소 목록(푸시, 커밋, PR)만 예시 설정 파일로 싣는다(2026-11-13 결정).

**말로 한 허용.**

- 허용은 그 턴이 끝나면 사라진다. "이번 세션 동안 계속"이라고 하면(설정의 `session_grant` 표현) 세션 동안 남는다.
- 금지 표현은 이미 준 세션 허용도 거둔다.
- 도구가 만들어 넣은 프롬프트로 이어지는 처리는 같은 턴으로 본다. 그런 프롬프트는 허용을 만들지도 끝내지도 않는다(2.2).

**결과물 검사.**

```yaml
check:
  target: commit_message     # command · commit_message · pr_body · last_message
  pattern: "^.{1,50}(\n|$)"  # 맞아야 하는 형식. not_pattern 은 있으면 안 되는 표현
  mode: block                # block 은 막고, log 는 기록만 한다
```

- 명령, 커밋 메시지, PR 본문은 도구 호출 직전에 Bash 명령에서 뽑아 검사한다. 검사할 항목은 그 호출의 동작과 `when`이 맞고 범위·자격을 통과한 것이다.
  - 커밋 메시지: `git commit`의 `-m`(여럿이면 빈 줄로 잇는다), `-F -`와 heredoc, `--amend -m`.
  - PR 본문: `gh pr create`·`gh pr edit`의 `--body`·`-b`, `--body-file -`와 heredoc, `gh api`로 PR을 만들거나 고치는 호출의 `-f body=…`.
  - 파일로 넘겨서 뽑을 수 없는 경우(`-F <파일>`, `--body-file <파일>`)와 본문이 없는 경우는 검사하지 않고 통과시킨다. 원장에는 `skip`으로 남긴다.
- `mode: block`에 걸리면 호출을 막고 사유(그 항목의 글과 걸린 검사의 대상)를 모델에게 돌려준다. 모델이 고쳐서 다시 시도한다. 여러 항목이 걸리면 사유를 한 번에 낸다. `mode: log`는 막지 않고 원장에만 남긴다.
- 마지막 응답은 턴이 끝날 때 검사한다. 걸리면 모델을 한 번 더 돌게 하되 세션당 3회까지만 하고, 같은 항목이 연속으로 걸리면 2번까지만 막는다. 한도를 넘으면 원장에만 남긴다. 이 검사의 항목은 범위·자격을 통과해야 하고 `when`은 `repo`·`agent`만 본다.
- 정규식은 Go 표준 문법이다. 앞뒤 살피기 문법은 없지만 시간 상한이 필요 없다.
- 식이 틀렸거나 heka가 실패하면 통과시킨다(R9).

### 3.4 등록

1. 인용을 대조한다: `source: user`이고 `quote`가 있으면, 최근 24시간 안에 고쳐진 세션 상태 파일에 적힌 세션 기록 파일을 읽어 사용자가 친 글과 공백을 정규화해 견준다. 세션 상태에는 기록 파일의 경로만 남고 프롬프트 글은 복사해 두지 않는다. 설정의 `claude_code.transcripts`(glob 목록)로 같은 형식의 다른 기록도 볼 수 있다. AI의 글, 도구 결과, 도구가 만든 프롬프트, 시스템이 넣은 표지로 시작하는 글, 메타·사이드체인 줄은 인용으로 인정하지 않는다. 기록 파일이 없거나 못 읽으면 그 파일은 건너뛴다. 확인되지 않으면 `quote`를 비우고 본문 끝에 "확인되지 않은 인용"으로 남겨 등록한다. 사람이 확인(`checked`)하기 전에는 주입되지 않는다(3.2의 자격).
2. 검증한다: 필수 필드, 주제어 1개 이상, 필수 항목이면 조건, 진행 상태면 기한. error가 있으면 등록하지 않고 문제 목록을 돌려준다.
3. 비슷한 항목을 찾는다. 다음 넷 중 하나라도 맞으면 비슷한 것으로 친다.
   - id가 같다.
   - 범위와 `when.action`이 함께 겹친다.
   - 주제어가 같다(공백을 지운 형태로 견준다).
   - 새 항목의 `text`를 질의로 한 낱말 점수가 0.5 이상이다(잠정).
4. 없으면 바로 쓰고 색인을 교체한다.
5. 있으면 대기함(`items/_pending/`)에 두고 후보를 돌려준다. 대기함의 항목은 주입하지 않는다.

| 결정 | 처리 |
|---|---|
| 고치기 | 기존 항목의 내용을 새 내용으로 고친다 (같은 id) |
| 바꾸기 | 기존 항목 파일을 지우고 새 항목을 등록한다 |
| 따로 두기 | 다른 항목이라는 이유를 본문에 적고 새로 등록한다. 같은 id가 있으면 할 수 없다 |
| 버리기 | 대기함에서 지운다 |

결정 없이 남은 등록은 `heka pending`으로 본다. 결정마다 색인을 다시 만들고 원장에 한 줄을 남긴다. 등록 자체를 거절하지 않는 이유는 교정이 사라지지 않게 하기 위해서다. 항목 저장소(`$HEKA_HOME`)가 git 저장소이면 쓴 뒤 커밋을 시도하고, 실패해도 등록은 성공이다. `checked`는 사람이 명령줄에서 직접 줄 때만 채우고 MCP로는 받지 않는다.

## 4. 기술 구조

```
 AI 도구 (Claude Code, Codex …)
     │ 이벤트                    ▲ 주입문
     ▼                           │
 ┌────────┐   순간   ┌────────┐  │
 │ 연결부 │ ───────▶ │ 선별기 │ ─┘
 └────────┘          └────────┘
                      │읽기  │기록
                      ▼      ▼
 항목 파일 ──색인──▶ 색인   원장 ──▶ 재현기 · 보고
   ▲
   └── 등록 (AI의 조회 도구, 명령줄, 사람의 직접 편집)
```

- **실행 형태**: Go 실행 파일 하나. 훅, 조회 서버, 명령줄이 같은 파일의 하위 명령이다. heka가 따로 띄워 두는 서버는 없다. 조회 서버(`heka mcp`)만 AI 도구가 세션 동안 띄워 둔다(4.5).
- **연결부**: 도구마다 하나씩 둔다. Claude Code 연결부를 먼저 만든다. AI가 직접 부르는 조회·등록은 MCP 서버로 낸다.
- **색인**: 항목 파일에서 만든 파일 하나. 쓰기 경로가 색인을 같은 호출 안에서 갱신하므로 등록 직후 주입된다.
- **원장**: 추가만 하는 줄 단위 파일. 집계는 읽을 때 계산한다.
- **데이터 위치**: 항목, 설정, 원장은 저장소 밖 `$HEKA_HOME`에 둔다. 사용자·조직마다 다른 값(저장소→범위 표 등)은 전부 설정 파일에 있고 코드 기본값은 비어 있다.
- **실패 처리**: 훅은 시간 상한 안에 답하지 못하면 아무것도 넣지 않고 끝낸다. 입력을 읽지 못하거나 처리 중 오류가 나도 같다. 어느 경우에나 종료 코드는 0이고, 오류는 `ledger/errors.log`에 한 줄 남는다. 모델 판정이 실패하거나 늦으면 그 후보만 넣지 않는다. `confirm` 항목도 같다. 어떤 경우에도 막아야 하는 행동(절대 금지)은 heka가 아니라 각 AI 도구의 권한 설정에 둔다(2026-11-13 결정).
- **훅의 한도**: 처리 시간 상한은 프롬프트와 서브에이전트 시작이 25초(판정 명령을 부를 수 있어서), 그 밖의 이벤트는 5초다. 그림자 방식(4.10)은 각각 60초와 10초다. AI 도구가 받는 글은 한 번에 10,000자까지이고 넘으면 뒤쪽이 잘린다.

### 4.1 색인의 내부

마크다운 파일만으로는 훅 한 번에 수백 개 파일을 읽고 해석해야 하므로 판정에 쓸 수 없다. 항목 파일과 설정 파일을 읽어 검증하고 엮은 색인 파일 하나를 둔다. 색인은 SQLite 파일이다(2026-11-13 결정, 4.7의 실측 참고). 데이터베이스 서버가 아니라 heka가 직접 여는 파일이고, 만들 때마다 임시 파일에 쓴 뒤 이름을 바꿔 통째로 교체한다. 그 안에 네 가지 조회 구조가 표로 들어간다. 항목 파일은 `items/*.md`만 읽고 대기함은 읽지 않는다.

| 구조 | 표 | 조회 | 쓰는 순간 |
|---|---|---|---|
| 조건표 | `item_when` | 동작 이름 → `when`이 걸린 항목 | 도구 호출 직전, 세션 시작 |
| 주제어 사전 | `item_about` | 글에 든 주제어 → `about`에 그 말이 있는 항목 | 프롬프트, 서브에이전트 시작 |
| 어휘 색인 | `lex`, `lex_df` | 글의 낱말 조각 → 항목, 조각별 문서 수 | 프롬프트, 조회, 등록 |
| 항목표 | `item`, `item_scope` | id → 주입문, 출처, 확인 여부, 기한, 범위 | 모든 순간 |

그 밖에 범위 포함 관계(`scope_in`), 동작 포함 관계(`action_in`), 동작 낱말 사전(`action_phrase`), 색인의 메타(`meta`: 항목 수, 만든 시각, 낡았는지 보는 지문)가 든다. 지문은 항목 파일과 설정 파일의 경로·크기·수정 시각을 해시한 값이다.

어휘 색인은 SQLite의 전문 검색을 쓰지 않는다. 항목의 `text`와 `about`에서 heka가 낱말 조각을 뽑아 `lex`(조각, 항목)에 넣고, 조각이 든 항목 수를 `lex_df`에 센다. 조각은 한글 낱말이면 연속한 두 글자 조각 전부이고, 영문·숫자 낱말이면 낱말 자체와 `_ - . /`로 나눈 길이 2 이상의 부분이다. 조각의 희소도는 항목 수 N과 조각이 든 항목 수 df로 ln(1 + (N − df + 0.5) / (df + 0.5))이다. 낱말 점수는 질의와 항목에 함께 있는 조각의 희소도 합을 질의 조각 전체의 희소도 합으로 나눈 값이다. 본문(`body`)은 색인하지 않는다.

설정 파일의 범위 표와 동작 분류가 작은 고정 어휘다. 범위는 포함 관계를 가지고(저장소 ⊂ 팀 ⊂ 조직), 동작도 포함 관계를 가진다(`git.push.force` ⊂ `git.push` ⊂ `git.write`). 동작의 상위는 설정의 `in`과 이름의 점 앞부분을 함께 본다(`pr.edit`은 `in: pr.write`와 점 앞부분 `pr`가 모두 상위다). 상위에 건 조건은 하위에도 걸리고, 하위에 건 조건은 상위 동작만으로는 걸리지 않는다. 강제 푸시에만 해당하는 규칙은 `git.push`가 아니라 `git.push.force`에 건다. 동작마다 그 동작을 시키는 표현을 적은 동작 낱말 사전(3.3)도 설정 파일에 있고, 색인에 함께 실린다.

### 4.2 훅 한 번의 처리

훅은 매번 새 프로세스로 뜨고, 색인 파일을 읽고, 판정하고, 끝난다.

```
도구 호출 직전:   도구 호출 → 동작 해석 → 범위·자격 → 조건표 조회 → 주입문
프롬프트 (동작):  프롬프트 → 동작 낱말 사전 → 시킨 동작 → 범위·자격 → 조건표 조회 → 주입문, 허용 기록
프롬프트 (주제):  프롬프트 → 조각내기 → 범위·자격 → 주제어 사전·어휘 색인으로 후보 → 모델 판정 → 주입 또는 침묵
위임 호출 직전:   위임 도구(Agent·Task) 호출 → 위임 글을 세션 상태에 적어 둠
서브에이전트 시작: 세션 상태에서 위임 글 꺼내기 → 범위·자격 → 시작 항목, 주제 갈래(프롬프트와 같음)
공통:             세션 상태로 중복 제거 → 예산 → 원장에 한 줄 → 출력
```

- 도구 호출 순간은 글의 표현과 무관하게 동작 이름으로 찾는다.
- 프롬프트 순간은 두 갈래다. 동작 조건이 붙은 항목은 동작 낱말 사전이 알아챈 동작으로만 찾고, 그 밖의 항목은 주제어와 어휘로 찾는다(3.2).
- 도구가 만들어 넣은 프롬프트는 두 갈래를 모두 건너뛴다(2.2).
- 주제 갈래는 조사가 붙은 한국어를 잡기 위해 어절과 두 글자 조각을 함께 쓰고, 흔한 단어는 희소도로 눌러 후보를 잡는다. 후보는 작은 언어 모델이 한 건씩 판정하고, 넣으라는 답이 없으면 아무것도 넣지 않는다(4.3).
- 모델을 부르는 것은 주제 갈래뿐이다. 도구 호출 직전과 동작 갈래는 모델을 부르지 않는다.
- 서브에이전트 시작 훅의 입력에는 위임 글이 없다. 그래서 위임 도구를 부르는 도구 호출 직전에 도구 입력의 프롬프트를 세션 상태에 적어 두고(에이전트 종류는 `subagent_type`, 없으면 `general-purpose`), 서브에이전트가 시작될 때 같은 종류의 가장 오래된 글을 꺼내 쓴다. 한 세션에 쌓아 두는 글은 16건, 글 하나는 4,000자까지다. 같은 종류의 서브에이전트를 동시에 여럿 띄우면 글이 서로 바뀔 수 있다. 글을 찾지 못하면 위임 글 없이 시작 항목만 고르고 참고 항목은 넣지 않는다.
- 세션 상태 파일은 이미 넣은 항목(주체별), 말로 한 허용, 기다리는 위임 글, 턴 종료 검사의 되돌림 횟수, 세션 기록 파일의 경로를 담는다. 고칠 때는 폴더 만들기로 잠금을 잡고 임시 파일에 쓴 뒤 이름을 바꾼다.

### 4.3 기술별 판단

| 기술 | 푸는 문제 | 드는 것 | 판단 |
|---|---|---|---|
| 조건표 | 행동 규칙이 프롬프트 단어에 의존하던 문제 | 셸 명령을 동작 이름으로 바꾸는 해석기 | 채택 |
| 동작 낱말 사전 | 행동 규칙이 프롬프트의 낱말에 우연히 걸려 생기는 잡음 | 동작마다 표현을 적는 일. 사전에 없는 표현은 프롬프트에서 놓치고 도구 호출 직전에야 준다 | 채택 |
| 주제어 사전 | 흔한 단어가 우연히 겹쳐 생기는 잡음 | 항목마다 주제어를 적는 일 | 채택 |
| 어휘 색인 | 주제어를 빠뜨린 항목 | 두 글자 조각을 heka가 만들어 조각 표(`lex`, `lex_df`)에 넣고, 점수는 겹친 조각의 희소도 합으로 heka가 낸다. SQLite의 전문 검색은 쓰지 않는다 (4.1) | 채택 |
| 고정 어휘 | 범위 누출, 같은 규칙의 중복 작성 | 설정 파일 | 채택 |
| 임베딩 | 표현이 다른데 뜻이 같은 경우 | 프롬프트마다 모델 호출. 로컬에 모델을 띄워 두어야 하고 지연이 붙는다 | 보류 |
| 작은 언어 모델의 판정 | 주제는 같은데 항목에 답이 없는 경우, 낱말은 겹치는데 관련이 없는 경우 | 프롬프트마다 모델 호출. 초 단위 지연이 붙고, 네트워크 왕복과 인증이 필요하고, 결과가 매번 같지 않을 수 있다 | 채택 (참고 항목에만) |
| 형태소 분석 | 두 글자 조각이 만드는 우연한 일치 | 사전을 품은 분석기. Go만으로 된 한국어 분석기는 성숙도가 낮다 | 보류 |
| SQLite 파일 | 색인 엔진을 직접 만들지 않아도 된다. 원장을 임의로 질의할 수 있다 | 의존 모듈 하나, 실행 파일 약 4MB 증가 | 채택 |
| 벡터 DB | 수십만 건 이상에서의 근사 검색 | 별도 저장소와 운영 | 기각 |
| 지식 그래프 | 여러 단계 추론, 시간에 따른 사실 변화 | 엔터티 추출, 동일성 판정, 검수 | 기각 |

동작 낱말 사전을 넣은 근거는 재현 세트의 비교다(2026-11-13). 기존 heka가 프롬프트 시점에 넣었던 사례 가운데 사람이 확인한 29건(넣어야 함 10, 넣지 말아야 함 19)으로 견줬다.

| 방식 | 넣어야 할 10건 중 넣음 | 넣지 말아야 할 19건 중 거름 |
|---|---|---|
| 기존 heka | 10 | 0 |
| 주제어 일치만 | 0 | 18 |
| 작은 언어 모델에 한 건씩 묻기 | 7 (다시 돌리면 5) | 17 (다시 돌리면 18) |
| 동작 낱말 사전과 주제어 일치 | 6 | 18 |

- 넣지 말아야 할 19건 중 13건이 동작 조건이 붙은 항목이었다. 기존 잡음의 큰 몫이 행동 규칙을 프롬프트의 낱말로 찾은 데서 나왔다.
- 사전과 모델은 이 자료로 구분되지 않는다. 넣어야 할 사례가 10건뿐이고, 사전은 사례 일부를 본 뒤에 적었고, 모델은 하나를 지시문 하나로 잰 값이다.
- 프롬프트에서 놓친 것을 도구 호출 직전에 주는 길이 실제로 메우는지는 구현 뒤에 잰다.

참고 항목의 선별에는 뜻의 신호로 작은 언어 모델의 판정을 넣는다(2026-11-14 결정). 속도보다 정확한 전달이 우선이기 때문이다(5장). 근거는 재현 세트의 비교다. 참고 항목을 묻는 말 14건과 조용해야 할 39건으로 견줬고, 모델은 하나를 지시문 하나로 두 번 돌렸다.

| 방식 | 묻는 말 14건 중 맞는 항목을 넣음 | 조용해야 할 39건 중 조용함 |
|---|---|---|
| 주제어 일치만 | 5 | 34 |
| 주제어가 일치한 후보를 모델이 판정 | 4 (다시 돌리면 5) | 39 (다시 돌리면 39) |
| 주제어 일치와 낱말 점수 상위 3건을 모델이 판정 | 12 (다시 돌리면 13) | 38 (다시 돌리면 36) |

- 주제어 일치는 후보를 적게 잡는다. 14건 중 5건만 후보에 든다. 낱말 점수 상위 3건을 더하면 13건이 든다.
- 낱말 겹침만으로는 넣을지를 가르지 못한다. 주제어를 뺀 나머지 낱말이 항목에 얼마나 있는지로 재 보았으나, 넣어야 할 것과 넣지 말아야 할 것 사이에 간격이 없었다. 그래서 낱말은 후보를 잡는 데만 쓴다.
- 후보를 넓게 잡으면 프롬프트 대부분에서 모델을 부른다(104건 중 96건). 프롬프트 한 건의 지연은 명령줄 도구로 불렀을 때 중앙값 3.0초, 95%가 5.3초 이내, 최대 8.6초였다(프로세스 기동 포함, 후보를 동시에 부름).
- 같은 쌍에 두 번 물어 답이 갈린 것은 254쌍 중 11쌍이다.
- 한계: 묻는 말과 조용해야 할 사례는 대부분 평가용으로 만든 문항이다. 넓게 잡아 넣은 쌍 24~27개 가운데 11개는 정답이 없어 맞는지 모른다. 지시문은 사례 일부를 본 뒤에 적었다.

**판정 명령.** heka는 모델을 직접 부르지 않는다(2026-11-15 확정). 설정 파일에 적힌 명령에 지시문과 프롬프트, 항목의 주입문과 주제어를 표준 입력으로 넘기고, 표준 출력에서 넣을지와 이유를 읽는다.

```yaml
judge:
  command: [my-model-cli, --model, small]   # 표준 입력으로 글을 받고 표준 출력으로 답하는 명령
  timeout: 15s                              # 기본값. 넘으면 그 후보는 넣지 않는다
  candidates: 3                             # 기본값. 낱말 점수로 잡는 후보 수
  votes: 1                                  # 기본값. 2이면 두 번 물어 둘 다 넣으라고 할 때만 넣는다
  instruction: |                            # 모델에게 주는 지시문. command가 있으면 필수
    (예시 설정 파일 참고)
```

- 명령에는 지시문, 항목의 id·주입문·주제어, 프롬프트(서브에이전트 시작에서는 위임 글)가 표준 입력으로 간다. 답은 `{"inject": true|false, "reason": "…"}` 꼴의 JSON 객체 하나이고, 앞뒤에 다른 글이 있어도 읽는다. 종료 코드가 0이 아니거나 시간이 넘거나 답을 읽지 못하면 그 후보는 넣지 않는다.
- 어떤 모델을 어떻게 부를지는 그 명령이 정한다. 선별기는 AI 도구를 모르는 채로 남는다(R7). 로컬 모델을 부르는 명령으로 바꿀 수 있다.
- 후보들은 동시에 부른다. 시간 상한을 넘거나 답을 읽지 못한 후보는 넣지 않는다(R9).
- 명령이 설정돼 있지 않으면 참고 항목은 프롬프트 순간에 넣지 않고 조회로만 찾는다.
- 판정의 답과 이유는 원장에 남는다(원칙 4).
- 프롬프트와 주입문이 그 명령으로 넘어간다. 바깥 서비스를 부르는 명령을 쓸지는 사용자가 정한다.

임베딩은 보류로 둔다. 임베딩은 주제가 가까운지를 재는 신호라, 주제는 같고 답만 없는 경우를 가르지 못할 것으로 본다. 재지는 않았다.

### 4.4 한국어를 다루는 법

| 문제 | 예 | 대응 |
|---|---|---|
| 조사와 어미가 붙는다 | "커밋 메시지를", "푸시하면" | 주제어는 어절의 앞부분에서만 맞는다. 맞은 자리 바로 앞이 글자나 숫자이면 맞지 않고, 뒤는 무엇이 붙어도 된다 |
| 두 글자 낱말이 많다 | "견적", "결제" | 세 글자가 아니라 두 글자 조각으로 색인한다 |
| 띄어쓰기가 흔들린다 | "커밋메시지", "커밋 메시지" | 글과 주제어를 소문자로 바꾸고 공백을 지운 형태끼리 견준다 |
| 영문·숫자 주제어가 더 긴 낱말에 든다 | "push"와 "pushed" | 영문·숫자로 끝나는 주제어는 맞은 자리 뒤도 영문·숫자가 아니어야 한다(낱말 경계). 뒤에 한글 조사가 붙은 것("push를")은 맞는다 |
| 뜻은 같은데 말이 다르다 | "삭제", "지워", "remove" | 글자 처리로는 풀 수 없다. 주제어에 다른 표현을 함께 적는다. 그래도 부족한지는 재현 결과로 본다 |
| 필수 규칙 | "요청 없이 푸시하지 않는다" | 글의 낱말이 아니라 동작으로 찾는다. 도구 호출은 동작 이름으로, 프롬프트는 동작 낱말 사전으로 알아챈다 (3.3) |

### 4.5 프로세스와 파일

서버도 데이터베이스 프로세스도 없다. 실행 파일 하나가 세 가지 방식으로 불린다.

| 진입점 | 누가 부르는가 | 수명 | 건드리는 파일 |
|---|---|---|---|
| `heka hook` | AI 도구의 훅 | 이벤트마다 떴다 끝난다 | 색인 읽기, 세션 상태 읽기·쓰기, 원장 줄 추가 |
| `heka mcp` | AI 도구 (조회·등록) | 세션 동안 떠 있다 | 색인 읽기, 항목 쓰기 후 색인 교체 |
| `heka find·add·pending·why·list·stats·retire` | 사람, 다른 도구 | 부를 때만 | 색인 읽기, 항목 쓰기(`add`, `pending`, `retire`)와 색인 교체, 원장 읽기·줄 추가 |
| `heka replay·judge-stats` | 사람 (재기) | 부를 때만 | `replay`는 색인을 읽고 판정 명령을 부른다. 원장과 세션 상태는 쓰지 않는다. `judge-stats`는 원장을 읽는다 |
| `heka index·select·resolve` | 사람 (점검용) | 부를 때만 | 색인 만들기·검증(`index`), 순간 하나의 선별 결과(`select`)나 도구 호출 하나의 동작 이름(`resolve`)을 JSON으로 보기 |

`heka version`과 `heka help`도 있다. `heka replay`는 사례 파일(JSONL)의 순간들을 선별기에 넣어 전달·정밀도·침묵, 걸린 시간, 넣은 글의 토큰을 재고, 합격선(`--min-delivery` 등)을 주면 못 미칠 때 종료 코드 1로 끝난다(5장).

프롬프트 훅은 참고 항목의 후보가 있으면 설정된 판정 명령을 자식 프로세스로 부르고 답을 기다린다(4.3). heka가 띄워 두는 것은 여전히 없다.

세션이 여럿이면 훅 프로세스가 동시에 여러 개 뜬다. 색인은 이름 바꾸기로 한 번에 교체하고 원장은 줄 단위로 덧붙이므로 서로 깨뜨리지 않는다. 항목 파일을 사람이 직접 고치면 다음 훅이 색인이 낡은 것을 알아채 다시 만든다.

### 4.6 훅과 MCP의 역할

둘 다 모델의 컨텍스트에 글을 넣는다. 다른 점은 누가 시작하느냐다. 빠뜨리면 안 되는 것은 훅이 맡고, 훅이 미리 알 수 없는 필요는 MCP가 맡는다.

| | `heka hook` | `heka mcp` |
|---|---|---|
| 누가 시작하나 | AI 도구의 하네스 | 모델 |
| 입력 | 이벤트: 프롬프트 글, 도구 호출 | 모델이 쓴 질의, 등록할 내용 |
| 하는 일 | 확신 있는 것만 짧게 넣는다 | 배경을 읽는다(`heka_find`). 교정을 등록한다(`heka_add`). 대기함을 결정한다(`heka_pending`). 틀린 항목을 표시한다(`heka_flag`) |
| 약점 | 미리 정한 순간과 조건 밖의 필요는 못 채운다 | 부르지 않으면 없다 |
| 훅이 없는 AI 도구 | 쓸 수 없다 | 유일한 경로가 된다 |

- MCP의 조회는 별도 조립기를 두지 않고 같은 선별기를 넉넉한 예산으로 돌린다. 작업용 컨텍스트 묶음을 만드는 전용 기능은 두지 않고, 그 쓰임은 조회 하나가 맡는다(2026-11-13 결정, 2026-11-16 다시 확인).
  - 낱말 나열뿐 아니라 작업을 설명하는 문장도 질의로 받는다.
  - 모델 판정은 부르지 않고, 동작 조건이 붙은 항목도 대상에 넣는다. 후보는 주제어가 질의에 든 항목과 낱말 점수 상위 K건(기본 5, 점수가 0보다 큰 것)이고, 범위·자격은 프롬프트 선별과 같은 규칙으로 거른다. 순서는 주제어로 걸린 것이 먼저, 그다음 낱말 점수 내림차순, 같으면 id 오름차순이다.
  - 항목의 주입문과 본문을 함께 돌려준다. 예산 인자를 받고(기본은 설정의 `budgets.find`, 잠정 1500토큰), 순서대로 넣다가 안 들어가는 항목은 본문을 빼고 주입문만으로 다시 시도하며(`body_omitted`), 그래도 안 들어가면 빠진 목록에 넣어 수와 id를 응답에 적는다.
  - 범위는 인자로 받고, 없으면 작업 폴더를 설정의 `locations`로 찾아 정한다(`global_scopes`는 늘 포함).
  - 조회는 세션 상태를 보지 않는다. 그 세션에 이미 주입된 항목도 결과에 들어간다(7장 9번).
  - 같은 조회를 명령줄(`heka find`)로도 낸다. 훅이나 MCP를 쓰지 않는 다른 도구가 부를 수 있다.
  - 묶음 안의 칸 구분, 모드, 조회 안에서의 필수 판정은 두지 않는다. 필수 항목은 행동 직전의 훅이 동작 이름으로 찾는다.
- MCP가 돌려준 항목도 원장에 남긴다. 같은 실행 파일이므로 이를 관찰하는 별도 훅이 필요 없다.
- 기존 heka의 두 달 실적은 훅 판정 9,574회, MCP 호출 1,301회였다. 서브에이전트 74개 중 스스로 조회한 것은 11개였다. 서브에이전트에게는 밀어 넣기가 사실상 유일한 전달 경로다.

### 4.7 색인 방식 실측 (2026-11-13)

훅은 이벤트마다 새 프로세스로 뜨므로, 색인을 여는 비용이 매번 든다. 두 방식을 같은 조회 세 가지(조건표, 주제어 사전, 어휘 색인)로 쟀다.

| | 직접 만든 파일 | SQLite 파일 |
|---|---|---|
| 훅 1회, 항목 500건 | 10.2ms (95%는 12.6ms 이내) | 11.2ms (95%는 21.5ms 이내) |
| 훅 1회, 항목 5,000건 | 20.1ms (95%는 22.8ms 이내) | 13.4ms (95%는 15.0ms 이내) |
| 색인을 여는 시간, 500건 → 5,000건 | 1.1ms → 8.1ms | 0.4ms → 0.4ms |
| 읽는 도중 색인 교체, 800회 실행 | 실패 0 | 실패 0 |
| 실행 파일 크기 | 2.1MB | 6.5MB |

- 아무 일도 하지 않는 프로세스가 뜨고 끝나는 데 7.2ms가 든다.
- 두 방식 모두 목표(S5, 50ms) 안이다. 속도로는 갈리지 않는다.
- SQLite 파일로 정한 이유: 색인 엔진을 직접 만들지 않아도 되고, 항목이 늘어도 여는 시간이 같고, 원장을 SQL로 질의할 수 있다.
- 함께 확인한 것: cgo 없이 Go만으로 된 SQLite 드라이버에서 전문 검색(FTS5)과 단어별 문서 수 조회가 동작한다. 세 글자 조각 방식은 두 글자 검색어를 찾지 못한다. 그래서 두 글자 조각은 heka가 직접 만들어 넣는다.
- 조건: Go 1.27, arm64 macOS, `modernc.org/sqlite` v1.62.0(SQLite 3.54.1), 프로세스 200회 순차 실행.
- 한계: 지어낸 데이터로 한 번 잰 값이고 디스크 캐시가 데워진 상태였다. 검색 품질은 재지 않았다. SQLite 500건에서 95% 값이 튄 원인은 조사하지 않았다.

### 4.8 파일 배치

```
$HEKA_HOME/
  items/*.md             정본. git으로 이력 관리
  items/_pending/*.md    대기함. 결정을 기다리는 등록. 주입하지 않는다
  config.yaml            설정 (아래 표)
  index/index.db         색인(SQLite 파일). 지우고 다시 만들 수 있다
  ledger/2026-11.jsonl   원장. 추가만 한다
  ledger/errors.log      훅의 오류. 한 줄에 시각, 이벤트, 내용
  sessions/<id>.json     세션 상태. 넣은 항목, 허용, 기다리는 위임 글, 세션 기록 경로
  replay/                재현 세트. 실제 데이터라 저장소에 넣지 않는다
```

`$HEKA_HOME`을 지정하지 않으면 `$HOME/.heka`를 쓴다. 설정 파일에는 모르는 최상위 키가 있어도 무시한다. 키는 다음과 같다(예시는 `config.example.yaml`).

| 키 | 뜻 |
|---|---|
| `scopes` | 범위 포함 관계. 순환이 있으면 오류 |
| `locations` | 작업 위치(`path`) → 범위(`scopes`)와 저장소 이름(`repo`). 가장 길게 맞는 것을 쓴다. `path` 끝의 `*`는 이름이 그 앞부분으로 시작하는 폴더들 |
| `global_scopes` | 작업 위치와 무관하게 늘 보는 범위 |
| `actions` | 동작 낱말 사전. 동작 이름마다 상위 동작 `in`과 표현 `phrases`(Go 정규식) |
| `negations`, `negation_window` | 시킨 것으로 보지 않는 부정·질문·조건 표현과, 표현이 끝난 뒤 그것을 찾는 글자 수(기본 8) |
| `session_grant` | 말로 한 허용이 세션 동안 남게 하는 표현 |
| `tool_actions` | 도구 이름, `Skill:<스킬 이름>`, `Bash:<명령 이름>` → 동작 이름. 키에 `*`를 쓸 수 있다 |
| `budgets` | 순간별 토큰 상한(`session_start`, `prompt`, `tool`, `subagent_start`, `find`). 훅의 순간은 기본이 제한 없음, `find`는 1500 |
| `judge` | 판정 명령. `command`, `timeout`(기본 15초), `candidates`(기본 3), `votes`(기본 1), `instruction` (4.3) |
| `claude_code` | Claude Code 연결부. `scopes`(그 연결부로 들어온 순간에 늘 붙는 범위), `tool_prompt_prefixes`(이걸로 시작하는 프롬프트는 도구가 만든 것), `transcripts`(인용 대조에 더 볼 세션 기록의 glob), `shadow`(그림자 방식, 4.10) |

가장 큰 복잡도는 "도구 호출을 동작 이름으로 바꾸는 일"에 있다. 셸 명령은 같은 동작을 여러 방식으로 쓸 수 있어서다. 

### 4.9 바깥 과정을 위한 창구

교훈을 에이전트 정의·스킬·검사로 옮기는 과정은 heka 밖에서 돈다(2.5). heka는 그 과정이 쓸 명령만 낸다.

| 명령 | 내는 것 |
|---|---|
| `heka list [--json] [--agent <종류>] [--must] [--flagged] [--find-only] [--violated N]` | 항목 목록(id, 필수 여부, 조건, 범위, 확인 날짜, 기한). `--agent`는 `when.agent`에 그 종류가 걸린 항목, `--must`는 필수 항목, `--flagged`는 원장에 표시가 남은 항목, `--find-only`는 조회 전용 항목, `--violated N`은 검사에 걸린 횟수와 표시 횟수의 합이 N 이상인 항목 |
| `heka stats <id> [--json]` | 그 항목의 주입 횟수, 마지막 주입 시각, 예산·중복·판정으로 빠진 횟수, 검사에 걸린 횟수, 표시 횟수와 마지막 사유. 훅의 줄만 센다 |
| `heka retire <id> --reason <글>` | 항목을 은퇴시킨다. 파일을 지우고 색인을 다시 만들고 원장에 사유와 함께 한 줄을 남긴다. 저장소가 git이면 사유를 커밋 메시지로 남기고, 이력은 git에 있다 |
| `heka why [--session <id>] [--last N] [--id <항목 id>] [--json]` | 원장의 최근 줄(기본 20)을 한 줄씩 보인다. `--id`는 그 항목이 넣어졌거나 빠진 줄만. 판정 기록이 있으면 항목별 답과 걸린 시간도 보인다 |
| `heka judge-stats [--json] [--since <날짜>]` | 원장에 남은 판정 시간의 분포(중앙값, 95%, 최댓값)와, 시간 상한을 줄였을 때 잘릴 판정 수와 그중 넣으라고 답한 수 |

"어겨진 횟수"는 heka가 스스로 셀 수 있는 것만 센다: 결과물 검사에 걸린 횟수와, 표시 도구(MCP의 `heka_flag`)로 표시한 횟수다. 글을 읽고 위반을 판정하는 일은 heka가 하지 않는다. 표시는 원장에만 남고 항목 파일은 고치지 않는다.

### 4.10 그림자 방식

다른 도구와 같은 세션에서 나란히 돌려 판정만 견주기 위한 방식이다. 환경 변수 `HEKA_SHADOW=1`이나 설정 `claude_code.shadow: true`로 켠다. 훅은 평소와 똑같이 고르고 기록하지만(선별, 세션 상태 갱신, 검사 판정, 원장) 표준 출력에는 아무것도 쓰지 않고 종료 코드는 0이다. 주입도, 확인 요구도, 검사로 막기도 없다.

- 원장 줄에 그림자 여부가 붙고 `heka why`는 `(그림자)`를 붙인다. 검사의 "막음"은 실제로 막았다는 뜻이 아니라 막았을 판정이라는 뜻이다.
- 훅을 백그라운드로 돌리는 것이 전제라 처리 시간 상한이 넉넉하다(4장의 훅의 한도).
- `heka hook --print-settings --shadow`는 명령이 `HEKA_SHADOW=1 heka hook`이고 각 훅이 비동기로 도는 설정 조각을 낸다. 설정 파일을 직접 고치지는 않는다.
- 갈아타는 순서의 첫 단계가 이 방식이다(6장).

### 4.11 원장에 남는 것

원장은 월별 파일(`ledger/YYYY-MM.jsonl`)에 한 줄씩 덧붙인다. 읽을 때는 모든 달을 읽고 깨진 줄은 건너뛴다. 훅의 줄은 세션 시작, 프롬프트, 서브에이전트 시작마다 남고, 도구 호출은 넣은 항목·탈락·확인·허용 사용·검사 중 하나라도 있을 때, 턴 종료는 검사한 것이 있을 때만 남는다. 조회, 등록, 대기함의 결정, 표시, 은퇴도 각각 한 줄을 남긴다.

| 필드 | 뜻 |
|---|---|
| 시각, 세션, 에이전트 | 시각(UTC), 세션 id, 서브에이전트 안의 호출이면 그 id |
| 이벤트, 순간 | 훅 이벤트 이름이나 조회·등록·표시·은퇴 같은 사건, 선별기의 순간 |
| 동작 | 도구 호출을 해석한 동작 이름 |
| 넣은 항목 | 항목 id, 그때 항목의 내용 해시, 넣은 이유 |
| 탈락 | 항목 id, 단계(범위·자격·일치·중복·예산·판정), 사유. 한 줄에 30건까지 |
| 시킨 동작과 거절 | 프롬프트가 시킨 동작, 부정·질문·조건으로 버려진 동작 |
| 허용 사용 | 확인 없이 진행하게 한 허용(동작) |
| 확인 | 확인을 요구한 항목 id |
| 검사 | 항목 id, 대상, 결과(pass·fail·skip), 막았는지 |
| 판정 | 판정 명령을 부를 때마다 한 건: 항목 id, 답, 걸린 시간(밀리초), 오류와 시간 초과 여부 |
| 모델 후보 | 모델이 목록에서 고른 기록(`judge.pick.mode: record`일 때만): 목록에 준 항목 수와 목록 글의 토큰 어림, 고르는 호출에 걸린 시간, 오류·시간 초과 여부, 목록에 없는 id를 답한 수, 고른 항목마다 id·바로 넣으라고 골랐는지·한 건씩 판정을 받았는지와 그 답·지금 방식의 판정을 다시 썼는지·판정 시간. 주입에는 쓰이지 않는다 |
| 토큰 | 넣은 글의 토큰 어림. `(UTF-8 바이트 수 + 2) / 3` |
| 프롬프트 | 프롬프트의 앞 200자. 도구가 만든 프롬프트는 건너뛰었다는 표시만 남는다 |
| 사유 | 은퇴의 사유 |
| 처리 시간, 그림자 여부 | 훅의 처리 시간(밀리초), 그림자 방식으로 돈 줄인지 |

## 5. 성공 조건

합격선은 2026-11-13에 확정했다. 재현 세트는 기존 heka의 원장과 과거 세션에서 만들되, 실제 데이터는 저장소 밖에 둔다.

| # | 조건 | 재는 법 | 목표 |
|---|---|---|---|
| S1 | 전달률 | 재현 세트의 행동이 따르는 사례에서, 알았어야 할 항목이 행동 전에 주입된 비율 | 필수 100%, 전체 90% 이상 |
| S1b | 조회 적중 | 재현 세트의 묻는 말에서, 맞는 항목이 조회 결과 3위 안에 든 비율 | 90% 이상 |
| S2 | 정밀도 | 실제 프롬프트 표본에서, 주입된 항목 중 관련 있는 비율 | 70% 이상 |
| S3 | 침묵 | 무관한 프롬프트 세트에서 아무것도 넣지 않은 비율 | 95% 이상 |
| S4 | 준수 | 주입된 필수 항목이 그 세션에서 위반된 건수 | 기존 heka의 절반 이하 |
| S5 | 속도 | 훅 1회 응답 시간. 모델 판정이 붙는 프롬프트는 따로 잰다. 등록 후 반영 시간 | 모델 판정이 없으면 95%가 50ms 이내. 있으면 95%가 6초 이내를 목표로 재기만 한다. 반영은 즉시 |
| S6 | 토큰 | 순간별 주입 토큰과 세션당 합계 | 재기만 한다 |
| S7 | 크기 | 테스트를 뺀 코드 줄 수, 직접 의존 모듈 수 | 재기만 한다 |
| S8 | 설명 가능 | 임의의 주입에 대해 이유를 한 명령으로 확인. 사용자가 구조를 직접 설명 | 둘 다 가능 |
| S9 | 실사용 | 2주 사용 중 "등록돼 있었는데 또 지적한" 건수 | 기존 heka의 4분의 1 이하 |
| S10 | 불필요한 확인 | 사용자가 그 턴에 시킨 일인데 확인을 요구한 횟수 | 0 |

S1~S3과 S5~S7은 재현기로 자동 측정한다. S4, S9, S10은 실사용 기록이 필요하다.

전달률은 두 가지로 나눠 잰다(2026-11-13 결정). 행동을 시키는 프롬프트와 행동 시점의 사례는 S1로, 행동 없이 규칙이나 지식을 묻는 말은 S1b로 잰다. 행동 규칙은 프롬프트의 낱말로 찾지 않으므로(3.2) 묻는 말에는 프롬프트 시점에 주지 않고, 조회로 찾아지는지만 본다. 에이전트가 조회하지 않아 비는 경우는 재현으로 잴 수 없고 S9에서 드러난다.

조건끼리 충돌하면 반복 실수 감소(S1~S4, S9)가 우선이다(2026-11-13 결정). 모델 판정이 없는 훅의 속도만 합격선을 본다. 토큰과 코드 크기는 합격 여부를 가르지 않고 재기만 한다(2026-11-16 결정). 바라는 것은 가볍거나 작은 것이 아니라 정확한 전달과 품질이다.

정확한 컨텍스트를 전달하기 위해서라면 속도는 양보한다(2026-11-14 결정). heka에 바라는 것은 빠른 응답이 아니라 정확한 전달과 그에 따른 결과물이다. 그래서 프롬프트 순간에 모델 판정을 기다리는 시간을 받아들이고, S5는 모델 판정이 없는 훅과 있는 훅으로 나눠 잰다.

참고 항목의 선별에는 모델 판정이 들어가 결과가 매번 같지 않을 수 있다. S2와 S3은 재현 세트 전체를 두 번 돌려 낮은 쪽으로 판정한다(2026-11-15 확정). 채점할 때의 일이고, 실제 사용에서 프롬프트마다 두 번 묻는다는 뜻이 아니다.

### 합격선과 기존 heka의 기준선

합격선은 두 단계로 둔다. 최소 합격선에 못 미치면 교체하지 않고, 목표에 닿으면 충분하다고 본다. S1~S3, S5, S6의 기준선은 재현 세트로 지금의 기존 heka를 잰 값이고(2026-11-13), 나머지는 기존 heka의 두 달 기록에서 센 것이다.

| # | 기존 heka의 기준선 | 최소 합격선 | 목표 |
|---|---|---|---|
| S1 전달률 | 필수 10건 중 9건, 전체 11건 중 9건 (82%). 프롬프트 시점만 잰 값이다 | 필수 95%, 전체 80% | 필수 100%, 전체 90% |
| S1b 조회 적중 | 22건 중 18건 (82%) | 80% | 90% |
| S2 정밀도 | 29% (넣은 31건 중 9건). 사람이 확인한 사례만 보면 17건 중 8건 | 50% | 70% |
| S3 침묵 | 39건 중 26건 (67%). 사람이 확인한 사례만 보면 10건 중 4건 | 90% | 95% |
| S4 준수 | 비율은 재지 못했다. 한 달 사건 23건 중 전달됐는데 어긴 것이 12건 | 같은 기간 건수가 늘지 않음 | 절반 이하 |

| S7 크기 | 약 18,500줄 (웹 화면 제외) | 두지 않는다 | 두지 않는다 |

- S8은 숫자가 아니라 되는지 안 되는지로 본다.
- 실측한 Go 방식의 훅은 10~20ms였다(4.7). 모델 판정이 없는 훅의 목표는 여유가 있다.
- 모델 판정이 붙는 프롬프트는 재현 세트에서 95%가 5.3초 이내였다(4.3). 속도로는 합격 여부를 가르지 않는다(2026-11-15 결정). 복잡한 항목을 판정할 때 더 걸릴 수 있어서다. 판정 명령의 시간 상한은 처음 10초였고 구현의 기본값은 15초다(잠정). 최종 값은 실사용으로 잰 뒤 정한다.
- 판정은 사람이 확인한 사례와 기존 판정대로 둔 사례를 합친 묶음으로 하고, 사람이 확인한 사례의 점수를 함께 적는다.
- 사례가 적어서 비율은 건수로 읽는다. 지금의 재현 세트에서 S1 필수의 최소 합격선은 12건 전부, S3의 최소 합격선은 39건 중 36건이다.
- S1의 기준선에는 행동 시점의 사건 2건과 기존 heka가 도구 호출 직전에 준 것이 빠져 있다. 둘 다 구현 뒤 도구 호출 재현으로 잰다.
- 기준선을 잴 때 사례에 적힌 범위를 함께 넘겼다. 실제 훅은 범위를 받지 않아, 견준 30건 중 5건에서 주입 결과가 달랐다.
- 재현 세트를 만들기 전의 기준선은 재는 방식이 달라 위 표에서 뺐다: 전달률은 사건 21건 중 13건, 정밀도는 사후 판정 54건 중 12건, 침묵은 평가 문항 35개 중 29개였다.

### 재현 세트

재현 세트는 이미 판정된 자료에서 만든다(2026-11-13 결정): 주입을 사후 판정한 것, 반복 실수로 기록된 사건, 평가 문항이다. 후보 목록을 만들고 사용자가 채택 여부를 판단한다. 기존 판정이 불명확하거나 사용자가 쓴 프롬프트가 아닐 수 있어 주의 표시가 붙은 후보는 사용자가 모두 본다. 표시가 없는 후보는 기존 판정대로 넣되 사람이 확인하지 않은 것으로 적고 점수를 따로 낸다. 새 구조에 대상 항목이 없어 잴 수 없는 후보는 뺀다. 실제 데이터이므로 저장소에 넣지 않는다.

기존 설계 점검표에 대한 판단은 다음과 같다.

| 점검 항목 | 판단 | 이유 |
|---|---|---|
| 관련도와 신뢰의 분리 | 채택 | 3.2 |
| 컨텍스트 조립 규칙 | 채택 | 본체다 |
| 평가 범주 (적중·침묵·범위 누출·낡음) | 채택 | S1~S3과 재현 세트의 범주 |

| 원천 버전 보존 | 기각 | 2.3 |

## 6. 기존 heka에서 가져오는 것과 두고 오는 것

두 달 동안 실제로 쓰인 것은 가져오고, 만들어 놓았지만 쓰이지 않은 것은 두고 온다. 숫자는 기존 heka의 기록에서 센 것이다.

| 가져오는 것 | 이유 | 실적 |
|---|---|---|
| 셸 명령을 동작 이름으로 바꾸는 해석기와 시험 사례 | 가장 복잡한 부분이 이미 Go로 있고 실제 명령 변형을 겪었다 | 판정 6,582회 |
| 줄 단위 원장과 파일 잠금 | 데이터베이스 없이 여러 세션의 동시 실행을 견딘 방식이다 | 약 11,000줄 |
| 말로 한 허용 | "푸시해 줘"를 그 턴의 허락으로 본다. 없으면 시킨 일에도 확인 창이 뜬다 | 91건 |

### 갈아타는 순서

새 heka의 조회 서버가 생겨도 기존 heka를 바로 떼지 않는다(2026-11-16 결정). 옮긴 항목은 자주 쓰인 것 일부이고 나머지는 기존 쪽에만 있기 때문이다.

1. 새 훅을 먼저 그림자 방식(4.10)으로 기존 훅 옆에서 돌려 판정만 견준다. 그림자 방식의 훅은 고르고 기록하되 내보내지 않으므로 기존 훅의 동작은 달라지지 않는다. 조회 서버는 등록해 기존 것과 함께 쓴다.
2. 옮기지 않은 나머지를 어떻게 할지 정한다. 한 가지 방법은 찾으면 나오지만 스스로 밀어 넣지는 않는 참고 항목으로 한꺼번에 옮기는 것이다. 조회 전용 항목(`push: false`)으로 옮길 수 있다.
3. 그 뒤에 기존 조회 서버와 훅을 함께 떼고, AI 도구의 지시 파일에 적힌 도구 이름을 고친다.

### 기존 Go 코드를 가져온 범위

기준(2026-11-13): 새로 써도 같은 코드가 되면 가져오고, 얻는 것이 분명한 부분만 새로 쓴다. 기존 훅 코드 5,713줄(시험과 외부 모듈 제외)을 이 기준으로 나눠 구현했다. 두 군데는 고쳐서 했다(2026-11-15 결정). 커밋 메시지와 PR 본문을 뽑는 부분은 버리는 층의 함수를 부르고 있어 고쳐서 가져왔고, 두 벌인 셸 해석기는 다른 언어에서 옮겨 온 쪽이 아니라 Go로 직접 쓴 쪽을 바탕으로 한 벌로 합쳤다. 표의 줄 수는 계획 당시 기존 코드를 센 값이고 지금 구현의 줄 수가 아니다.

| 구분 | 무엇 | 분량(계획 당시) | 결과 |
|---|---|---|---|
| 가져왔다 | 셸 명령 나누기, 앞에 붙는 말 벗기기, git 하위 명령 찾기, 강제 푸시 판별 | 531줄 | `internal/shell`. 외부 의존이 없고 새로 써도 같은 코드가 된다 |
| 고쳐서 가져왔다 | 커밋 메시지와 PR 본문 뽑기 | 454줄 | `internal/shell`. 결과물 검사(3.3)에 쓰인다. 파일 쓰기 대상 뽑기는 동작 해석 쪽(`internal/action`)에 있다 |
| 가져왔다 | 세션 상태 파일의 잠금, 원장 줄 덧붙이기 방식 | 480줄 | `internal/session`(폴더 만들기 잠금과 이름 바꾸기), `internal/ledger`(줄 단위 덧붙이기). 두 달 운영에서 검증된 방식이다 |

## 7. 열린 결정

1. 5장 합격선 숫자의 확정: 닫았다(2026-11-13). 재현 세트로 기존 heka를 잰 뒤 예시로 적었던 숫자를 그대로 확정했고, 전달률은 행동이 따르는 사례와 묻는 말로 나눠 잰다
2. 재현 세트의 확정: 닫았다(2026-11-13). 주의 표시가 붙은 후보는 사용자가 판단했고, 나머지는 기존 판정대로 넣어 점수를 따로 낸다(5장). 행동 시점의 사례는 구현 뒤에 잰다
3. 기존 Go 코드를 가져오는 범위: 닫았다(2026-11-15). 6장의 표대로 하되 두 군데를 고쳤고, 구현에 반영됐다
4. 뜻의 신호가 필요한지, 필요하다면 무엇으로 낼지: 닫았다(2026-11-14). 속도보다 정확한 전달이 우선이라는 결정에 따라, 참고 항목의 선별에 작은 언어 모델의 판정을 넣는다. 임베딩은 보류로 둔다(4.3)
5. 기존 항목의 변환: 닫았다(2026-11-13). 자주 쓰인 것만 옮기고 사용자가 한 건씩 확인했다
6. 데이터 폴더의 기본 위치: 닫았다(2026-11-15). `$HEKA_HOME`을 지정하지 않으면 `$HOME/.heka`를 쓴다
7. 참고 항목의 선별: 방향은 정해졌다(2026-11-14). 조회에만 맡기지 않고 heka가 주입하며, 후보를 모델이 판정한다(3.2, 4.3). 남은 것은 두 가지다
   - 후보 범위: 주제어 일치와 낱말 점수 상위 3건(`judge.candidates`, 기본 3)을 한 번씩 묻는 것(`judge.votes`, 기본 1)을 잠정으로 쓴다. 두 번 물어 둘 다 넣으라고 할 때만 넣게 바꿀 수 있다. 설정값으로 바꿀 수 있게 구현돼 있다. 2026-11-17 실험에서 묻는 말의 낱말을 바꾸고 항목을 약 250건으로 늘리면 스크립트 후보에 맞는 항목이 드는 수가 16건 중 10건에서 4건으로 줄었고, 모델이 목록에서 고르면 13건에서 12건이었다. 모델이 고른 것을 그대로 넣으면 틀린 주입이 늘었고(사람이 판정한 것 중 15%, 지금 방식 8%), 한 건씩 판정을 거치면 지금 방식과 같은 수준이었다. 실사용 기록을 본 뒤 후보 잡기를 바꿀지 정한다(기록 갈래는 3.2)
   - 판정의 시간 상한: 구현의 기본값은 15초(`judge.timeout`)이고 잠정이다. 판정마다 걸린 시간이 원장에 남으므로(4.11), 실사용 기록을 `heka judge-stats`로 본 뒤 정한다
   - 정해진 것(2026-11-15): 모델은 설정 파일의 판정 명령으로 부른다. 속도는 95%가 6초 이내를 목표로 재기만 한다. S2와 S3은 두 번 돌려 낮은 쪽으로 판정한다
8. 서브에이전트를 시작할 때의 참고 항목 선별: 닫았다(2026-11-15). 프롬프트 순간과 같은 방식(후보와 모델 판정)을 쓴다. 위임 글은 위임 도구 호출 직전에 세션 상태에 적어 둔 것을 쓴다(4.2). 재현 세트에 그 순간의 사례가 없어 구현 뒤 실사용 기록으로 잰다
9. 조회의 세부: 아직 열려 있다. 정한 것 하나와 잠정값 둘이 있다
   - 낱말 후보 수: 기본값을 10에서 5로 줄였다(2026-11-16). 재현 세트의 묻는 말 24건에서 맞는 항목이 결과에 든 것은 둘 다 22건이고, 돌려준 글은 평균 1,409토큰에서 1,240토큰으로 줄었다. 3으로 줄이면 19건으로 떨어진다
   - 기본 예산: `budgets.find`의 1500토큰
   - 그 세션에 이미 주입된 항목: 조회가 세션 상태를 보지 않으므로 지금은 결과에 다시 들어간다
